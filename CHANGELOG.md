# Changelog of the libretro core

What changed in the libretro core of this fork, newest first. Changes that come with a merge of upstream RPCS3 are in upstream's own history; a merge is noted here with the upstream build it brought in.

## Unreleased

- A packet received for a P2P datagram socket is copied once on its way to the game's read, where it was copied twice into two vectors and queued in a `std::queue`. The queue is a `retro_deque` of plain packets, each with a block of its own filled straight from the receive buffer and freed when the game has read it. A packet in and out, built with the core's flags: 19 ns where it took 38 at 64 bytes, 41 where it took 76 at 1200. A savestate has the queue as it had it, byte for byte - and no longer empties it: saving took every waiting packet out of the queue, which standalone RPCS3 can afford because it stops after saving, and here lost them for the game that carries on. `test_plain_queues` runs the queue against the one it was and the savestate both ways. Not run with a game on a network.
- A decoded video picture goes from the decoder to the game without the heap or a shared count. cellVdec kept each AU's pictures in a `std::deque` made anew for every AU and the pictures waiting for the game in another, and every frame owned its picture's buffer through a `shared_ptr` to the pool, counted up and down each time a frame moved. The frames are plain data in two `retro_deque`s made with the decoder, the pool is the decoder's own, and a buffer is given back to it by hand wherever a frame leaves a queue: taken by the game, flushed by a new sequence or a close, left by an aborted AU, or still queued when the decoder goes. One picture's trip - decoded, queued, handed on, taken - built with the core's flags: 33 ns where it took 44 to 48, 308 instructions, 6 calls and 1 locked operation where there were 368, 28 and 11. `test_vdec_frames` counts the buffers through 10000 pictures and every one of those ways out. Not run with a movie: that is the check this needs.
- Four more `std::deque`s gone. The timer thread's list of timers is a `retro_deque` made for every timer there can be (8192, 64 KB), each element a held reference kept as plain bytes: creating and destroying a timer no longer takes a block from the heap or gives one back, and takes 4 ns of list work where it took 15 (121 instructions against 146); the thread's pass over the timers is the same 33 instructions and the same time. cellVoice's queues to notify were a map of `std::deque`s and are one list of key and source, written to a savestate as the map was - the map's own code reads it back, and the reverse. cellSysutil's callback abort handles were a `std::deque` used as an array that does not move, and are an array. `sys_tty`'s input queues are removed: only standalone RPCS3's debugger window ever put anything in them, so a read finds no input, as it always did here. `test_held_queues` runs the timer list against the `std::deque` of `shared_ptr` it was for 200000 creates and destroys, counting every reference, and the cellVoice savestate both ways. Not run with a game.
- The plain-data queues are `retro_deque` too: RSX's frame-time and recovered-command histories, `sys_usbd`'s pending events, the Skylander, Infinity, Dimensions and Kamen Rider figures' statuses and replies, and a P2P stream socket's backlog were `std::queue` and `std::deque`, which take a block from the heap and give one back every few dozen elements for as long as they are used. Each is made once for the most it is expected to hold; the ones that had no limit of their own are pushed with `retro_deque`'s new `push_back_growing`, which reserves twice as much only if that is ever reached, so nothing is dropped that was not before. The backlog is written to a savestate as the `std::deque` was, byte for byte. Against the `std::` containers built with the core's flags: RSX's frame-time step (60 times read, the oldest dropped, one added) 40 ns where it took 160, in 146 instructions and 2 calls where there were 345 and 10; a 32-byte reply queued and taken is the same time within the noise (7.3 ns against 7.6), in 107 and 21 instructions where there were 168 and 42, with no block taken every sixteen replies. `test_plain_queues` runs the Skylander portal's own code, the backlog's savestate against a `std::deque`'s, and the other patterns against the containers they were. The header's casts are C++'s when a C++ file includes it, so the warning is no longer turned off around its uses. Not run with a game or with one of these devices.
- The lv2 event queues and the scheduler's lists are libretro-common's `retro_deque` (new there: a double-ended queue of one type in one block, C89), in place of the ring and the vectors that had replaced their `std::deque`s. One container for both, with nothing of the C++ library in it: a queue holds exactly its size, the scheduler's deadlines are inserted in order and the earliest taken off the front in one step where a vector moved the rest down. Against `std::deque` built with the core's flags: an event sent and taken 4.2 ns where it took 5.7 (21 instructions and no call to send one, where there were 41 and a call into the allocator's path); a scheduler step with 4, 16 and 64 threads asleep 8.4, 14.1 and 40.0 ns where it took 11.9, 21.3 and 60.8, in the same order over two million steps; no allocation in either, where `std::deque` made 250000 in four million events. A savestate still has an event queue byte for byte as before, now written without a `std::deque` to copy into; `test_lv2_events` reads a queue back from one. The SPU's and the RSX's reads of an event queue go through the same calls.
- A thread going to sleep with a timeout, or waking from one, allocates nothing. The lv2 scheduler keeps the sleeping threads' deadlines in a list, the earliest first, and another list of threads about to sleep; both were `std::deque`, which takes a block from the heap and gives one back as its contents move along - every few dozen timed sleeps, under the scheduler's lock, all through play. A thread is in each list once at most, so room for as many as there can be threads (100 PPU and 1535 SPU) is set aside when the core is loaded - 26 KB for the deadlines, 13 KB for the other - and the lists never ask for more. The order of the deadlines, and of threads with the same deadline, is as it was. The library tests fail if a `std::deque` comes back into the scheduler or the event queues.
- Sending and receiving an lv2 event allocates nothing. Every event queue kept its events in a `std::deque`, which takes a block from the heap for every sixteen events sent and gives one back for every sixteen received, all through play: games send events constantly, and cellAudio alone sends each of its queues one every 5.3 ms. A queue holds 127 events at most, a number it is given when it is made, so the events are now a ring of that many made with the queue. 100000 events through a queue allocate nothing; a `std::deque` under the same traffic allocates 6259 times (counted in a program of its own, not in the old core). A savestate has the queue byte for byte as it had it. `test_lv2_events` checks the order round the ring, the queue's limit, the allocations, draining, and the savestate's bytes against a `std::deque` of the same events.
- cellAudio's mixer four samples at a time on ARM as well (NEON), and the same number on every machine. A multiply and an add in the mixer stay two operations: GCC fuses them into one on ARM for the build's C standard unless told otherwise, which made a sample's last bit depend on the compiler and on whether a frame went through the vector path. `test_audio_mix` is built for ARM64 and run under emulation in CI (`make -C rpcs3/libretro/tests check-arm64`): the 3240 blocks against the code replaced, none differing; without the instruction to keep them apart 1192 differ there.
- cellAudio's mixer takes a third to two thirds of the time. Every 5.3 ms each open port's block of 256 frames is added into the block that goes on to the frontend; the loop looked at the port's volume setting before every frame (it steps for 13 ms after a cellAudioSetPortLevel) and swapped, scaled and added one sample at a time, with the audio mutex held throughout. The setting cannot change while the mutex is held, so it is read once a block: frames are still mixed one at a time while the volume is on its way, and once it is there - nearly always - four samples at a time (SSE2). A stereo port into stereo takes 126 ns a block where it took 406, a 7.1 port into 7.1 463 where it took 1391, a 7.1 port down to stereo 607 where it took 941 (against the old loops in C, in the same test). It is C89 (`cellAudio_mix.c`). Every sample is the same number, bit for bit: `test_audio_mix` runs 3240 blocks - ports of one, two and eight channels into two, six and eight, each downmix, volumes standing, rising, falling, arriving and not, samples at odd addresses, infinities and denormals among them - against the code replaced, and none differs.
- An emulated controller's poll allocates nothing. The USB controllers, the arcade board and the PS Move's stand-ins hand the configuration a callback for each poll of the pad; it was taken as a `std::function`, made anew every poll, and a callback that holds on to more than two things - the arcade board's, the guns', the PS Move's - was put on the heap for it and freed again: an allocation a poll, mid-game. The pad was passed as a `std::shared_ptr` of its own as well, its count written up and down by every thread polling it. The callback is called as what it is and the pad is borrowed. A poll of the pressed buttons takes 123 ns where it took 148, of all sixteen 211 where it took 250, with a callback small enough not to have been allocated; the others save the allocation too. `test_pad_buttons` counts what 1000 polls with a callback holding six things allocate: 1000 before, none now.
- Reading and writing files through the frontend no longer counts bytes. Every read and write added its length to one counter shared by all threads, and every open to another - statistics nothing ever read. With several threads on files of their own (the SPU workers, the caches, the game's readers) that one counter was the thing they all waited on one another for: the core's own part of a read at an offset took 17 to 20 ns with four threads on four files, and takes 2. The counters are gone, with 340 lines nothing called: a second file class with a `FILE*` fallback and helpers for stat, mkdir, rename and remove that `fs::` never used. `test_vfs_positional` times the four threads (VFS_BENCH=1); the library tests fail if such a counter comes back.
- A retro_run asks the frontend about the light guns only while something reads them: 119 calls into the frontend a run where there were 155. The guns are the PS3's mice, which few games set up; the 36 calls a run (nine a port) were made for every game. They start with the run after a game or an emulated device (the arcade board, a USB gun) sets the mice up, and the mice start from where the guns are then; the arcade shooter mode reads them regardless. Finding the mouse handler each run no longer asks for its type (a `dynamic_cast`). `test_input_poll` counts the calls with and without the mice and checks that a gun no longer read is no gun; `test_mouse_handoff` that nothing is asked before the mice exist and that the mice start at the guns' position, not at a gun that was never read.
- A pad nobody is touching costs next to nothing on either side. Each retro_run handed every pad's buttons and sticks over to the game's threads again - some sixty atomic stores a pad - whether or not anything had changed, and every cellPadGetData read all of it back and went through each button's switch to find that nothing was new. The frontend's thread now hands over only what differs from what it handed over last, and counts those; cellPadGetData works a hand-over into the port's data once and, while the count stands, reads nothing. cellPadGetData with nothing new takes 15 ns where it took 76 to 90, and the game's threads no longer have the pad's cache lines taken from them sixty times a second. What the game gets is the same: a buffer cleared with a button still held has the button in the next data (the hand-over is worked in again), a new pad object does not take the old one's count, and a hand-over that changes nothing the game sees is still worked in once. `test_pad_guest` checks each of those, and that 100 runs of an untouched pad hand over nothing; it fails with the clearing left out, and with the unseen hand-over not kept.
- Reading a pad each retro_run takes a third of the time: 51 ns a pad where it took 142 to 177 (the same machine, minutes apart). Two things went. RPCS3 pushes a stick's circle out toward a square, as a DualShock 3 reports it, with an arctangent, a square root, two sines, a cosine and three powers for each stick of each pad each frame; a stick has 256 by 256 positions, so that is now a table (128 KB), filled once at start from RPCS3's own function and read with one load a stick. And each of a pad's seventeen buttons went through two nested switches to find the frontend's button it stands for; which button is which is worked out when the pad is bound. Both are in the C89 `libretro_pad_values.c`. `test_pad_handoff` runs all 65536 positions of both sticks, with the buttons and pressures changing along, against the code replaced (kept in the test): no button and no stick differs. With the table filled the wrong way round it fails.
- The frontend reads the game's audio from cellAudio's own ring: the copy into a buffer of the core's on the way is gone. Each retro_run copied a frame's worth out of cellAudio's ring (under a compare-and-swap of two counters, copied again if it lost the race) and handed the copy over. retro_run now borrows it where it lies - a pointer into the ring - hands that to the frontend, and gives it back; floats for a frontend that takes none are converted straight from the ring. The ring is libretro-common's lock-free single-writer, single-reader one (`retro_spsc`) behind `libretro_audio_ring.c` (C89), its memory mapped twice back to back so that what is waiting is one piece even across the wrap. The old ring was one byte longer than a whole number of frames: after its first lap every sample lay at an odd address and a frame straddled its end, so it could not have been lent. A flush (the emulator pausing) is a mark the writer leaves and the reader skips to; what the reader has borrowed stays whole until it gives it back. When the ring has less than is due it is copied out and the rest is silence, as before; a platform that cannot map the ring twice copies at the wrap. The RSX audio path keeps its write callback. Handing over a run of 800 stereo frames takes 12 ns where pulling a copy first takes about 60 (against a frontend that does next to nothing with it). `test_audio_ring` (also under ThreadSanitizer) checks order across the wrap for 8-, 24- and 4-byte frames, the room, the flush, and a writer flushing against a reader on another thread; `test_audio_frontend` checks that all 200 of 200 runs hand the frontend memory inside the ring, the samples in order, silence when short, and nothing from before a flush after it; `test_audio_handover` runs the lending path against the old code for nine more cases.
- The game's audio goes to the frontend in one piece a retro_run. A run's worth (800 frames at 60 runs a second) was pulled from cellAudio and handed over 512 frames at a time: two pulls and two calls into the frontend every run, and the speaker layout worked out again for each. It is one pull and one call at any rate from 47 runs a second up, and the layout's speakers are worked out when the audio is opened. This part of the core is now C89 (`libretro_audio_out.c`: the pacing, the silence while nothing plays, the conversion to s16 for a frontend that takes no floats); `LibretroAudioBackend` keeps only what RPCS3's audio interface needs of it. The same samples, the same amount every run. `test_audio_handover` runs it against the code it replaces, kept there as the reference, on the same stream for fourteen cases (floats, s16, the classic stereo callback, 5.1, 7.1, NTSC, 50 and 30 runs a second, silence, short pulls): identical output, half the calls. Against a game's side and a frontend that do next to nothing, a run takes 47 ns where it took 53 with floats handed over, 254 where it took 263 converting to s16; the calls saved cost more in the core, where each pull goes through cellAudio's ring and each call through the frontend. The core's own copy of the multi-channel audio declarations is gone: libretro-common's `libretro.h` has them.
- retro_run no longer waits for the game to tell it of a pad connected or disconnected. The event goes to sys_io's queue for the game's handler thread, and sending it took sys_io's mutex - which a game's thread holds through cellPadEnd, cellKbEnd or cellMouseEnd while it waits for that handler thread to end, and through the calls that start it. The frontend's thread waited with it. The queue is now behind a gate of one atomic word: a send goes through if sys_io is started and is dropped if not, as before, without waiting; the game's thread stopping sys_io closes the gate once no send is under way, and only then destroys the queue. The mutex stays between the game's own threads, as a mutex of the PS3's would. `test_sys_io_gate` sends while a thread holds the mutex (the send did not return before), and stops and starts 200000 times against a thread sending: no send is ever under way at a stop (547 were, with a stop that does not wait for them).
- The PS3 mice (the light guns) take no lock. cellMouse, cellGem, the arcade board and the emulated guns each took the mouse handler's lock to read a mouse, and whoever held it replayed what retro_run had left on a ring per gun. A mouse is now a record read whole and changed whole (`retro_cas_record`), with the data waiting for cellMouseGetData in it; retro_run writes the guns' moves, presses and wheel turns to a log that is read without being emptied, and whichever thread reads a mouse applies what the log has past what the mouse already had. Of several threads taking a mouse's data, each piece goes to one. Those that only want where the mouse is and what it holds (cellGem, the board, the guns) read a small record of their own, which takes the same events the same way. A mouse nothing read while the log went round catches up with where the gun is, as before. Reading a mouse takes 10 to 12 ns where taking the lock and looking at the rings took 18 to 21 (a stand-in for the old code, timed in the same run); cellMouseGetData with nothing waiting takes 6 ns and writes nothing. The mouse's lists are fixed arrays in the record, no longer `std::deque`s; the tablet and raw data lists, which nothing ever filled, are gone, and so is a host-clock timer nothing used. `test_mouse_handoff` has four threads take 20000 moves from one mouse while retro_run makes them (each taken once; 2 checks fail with a lost race not made again), checks cellMouseGetData's and cellMouseGetDataList's ways of taking, the catch-up, and that the mouse never moves back for two readers with the gun flat out, one of them away for longer than the log.
- cellGem's camera tracker hands its results over without a lock, the last lock of cellGem's own. What it finds in a frame - the four spheres, and how many pixels there are of each hue - was written and read under the tracker's lock, which cellGemIsTrackableHue and cellGemGetAllTrackableHues took on every call, with or without a real PS Move. The spheres are one record read whole (a sphere's position always goes with its radius) and each hue's count a word of its own. `test_gem_shared` has three threads read the spheres while they are published 200000 times: none torn (24 of 1.3 million with the record written in place).
- cellGem (the PS Move) takes no lock for what it keeps. Its thirty calls, the Gem thread and the camera tracker shared one lock; what they share - the attributes, the four controllers, the flags and counters - is now one record read whole and changed whole (`retro_cas_record`): a call that reads copies it out, a call that changes it works on a copy and puts it back if the record is still the one it read, and is made again on the newer one if not. A check and the change that follows it are still one step (of four threads calibrating a controller at once, one starts it). Three things upstream's code did under the reader's side of the lock, or under none, are whole changes now: the sharpshooter's firing mode and the sphere's visibility written while reading a controller's state, and cellGemReset and cellGemPrepareVideoConvert, which took no lock at all. cellGemInit marks cellGem as starting until the record is set up, and cellGemEnd as ending until the memory is out of it. A read of the record takes 8 ns where the reader's side of the lock took 16 to 19; a controller's state read that changes nothing costs what the lock did (about 20 ns). The savestate is as it was. The tracker's results and the mouse handler keep their own locks for now. `test_gem_shared` clears a controller's 64 status flags a bit at a time from four threads among four other writers, 300 times over, and has four threads calibrate at once 2000 times; with a lost race not made again the flags are left set.
- An emulated controller reads its buttons from the pad's without a lock. The USB controllers, the arcade board and the PS Move's stand-ins look up, for every button of the pad on every poll, which of their own buttons are on it; that took the configuration's lock for each button - sixteen and more times a poll - and held it while the caller's code ran, so two threads polling waited on one another, and it went through two maps and a set. The mapping is now a small table sorted by pad button, copied whole once a poll (in atomics under a sequence count, written when a configuration is loaded) and searched in place: a poll of the pressed buttons takes 146 ns where it took 204, of all sixteen 253 ns where it took 470. It also holds the buttons' values and not the configuration's own objects, which a poll read while a load was writing them: a poll gets one whole mapping, where it could get the old mapping's buttons with the new one's values. `test_pad_buttons` checks every lookup, that a poll no longer waits for another thread's, and four threads polling while the mapping is made again 20000 times (5 polls of 40000 were mixed before; none now).
- The pad lock is gone. After cellPad, the rest that took `pad::g_pad_mutex` takes nothing: cellGem (the PS Move, 18 places), the emulated USB controllers (Buzz, the guitar, the turntable, the drawing tablet, the GunCon 3, the Top Shot guns, the arcade board), the native overlays' input and the pad thread. They read the pads through what retro_run hands over, which never needed it. Two things the lock had been covering in cellGem are done without it: a controller's external port (its status and device, asked for by several of the game's threads at once) is in atomics, and a DualShock 3 standing in for a PS Move no longer writes that device into the pad's PS Move data or keeps its button combinations in one set shared by every thread. The library tests fail if a merge of upstream's code brings the lock back.
- Version 2 of libretro's Vulkan context negotiation, with a frontend that has it (RetroArch does). With version 1 the frontend made the instance from the core's application info and handed the core a list of device extensions and features to merge into its own. With version 2 the core says what it wants of the instance and of the device, and the frontend's own wrappers create them with what the frontend needs added: its extensions where the GPU has them, its features in the pNext chain, queues of its own. RPCS3's instance extensions (MoltenVK's settings on Apple systems, the debug ones when asked for) can be asked for at all this way. A frontend with only version 1 is given version 1, as before. The core's Vulkan header is libretro-common's (it had a copy of its own). `test_vk_negotiation` is the frontend for both versions, on a software Vulkan driver in CI: the instance and the device each made once, by the frontend's wrapper with version 2 and never by the core, with the extension the frontend added; with the core made to call vkCreateDevice itself it fails.
- cellPad takes no lock. Every cellPad call took the pad lock, so the game's threads calling it took turns. What cellPad keeps of a port (what it last gave the game, the port's setting, what it reported of the device, a custom controller's registration and data) is now one record in the port's pad, read whole and changed whole with libretro-common's `retro_cas_record`: a call is one change of one port, and of two threads at the same port one goes first and the other works on what it left, as the lock had it. A custom (LDD) controller's port goes to exactly one of the threads registering. The savestate is as it was.
  - cellPadGetData with nothing new for the game - most calls - reads the port (4 ns) where it took and gave back the lock (9.5 ns), and writes nothing another thread reads; with something new it puts the port back with one compare-and-swap (28 ns), at most once a frame a pad.
  - With the motion sensors on, cellPadGetData reports every 10 ms with no change of input, as a DualShock 3 does. That was 10 ms of the host's clock: the reports kept the host's pace while fast-forwarding and went on through a pause. It is the PS3's clock, which follows retro_run.
  - cellPadSetActDirect no longer writes the motors' values and the time into the pad's plain fields, which only the standalone's device handlers read: two threads would have raced on them.
  `test_pad_guest` has four threads calling cellPadGetData while the buttons change 500 times (each change given to the game once), two threads changing a port's setting at once, eight threads registering custom controllers on six ports and four registering and unregistering 20000 times, and the sensor reports against both clocks. With a lost race in cellPadGetData not made again, 1087 changes are given for 500.
- A fresh tree builds without thousands of failed compiles: since the last change to the Makefile, `make` tried to build every dependency file it did not have yet from a source named after it.
- A retro_run asks the frontend only for the input something reads. Each run also read the mouse's movement and buttons, the pointer and 65 keyboard keys, and the motion sensors (switched on at start), into state nothing looked at: 78 of the 233 calls into the frontend a run, and six more for the sensors. They are gone: 155 calls a run, and the sensors are left off. Reading the frontend's input is now C89 (`libretro_input.c` in place of the C++): the same values in the same places for the pad and mouse handlers, which borrow them by pointer; 2754 bytes of code where there were 5497, and a poll takes 277 ns where it took 447 against a frontend that answers at once (the best of seven runs each). The line written to the log at each change of a pad's motors went with it. `test_input_poll` counts every call by device and checks each value, the arcade shooter mode, and that the frontend hears of the motors only when they change.
- A tree built before a source was converted from C++ to C builds on: `make` stopped at "No rule to make target" for the C++ file its dependency files still named.
- Files through the frontend take no lock where the frontend reads and writes at an offset (VFS v6, new in RetroArch). The frontend's handle had one position, so every read, write, seek and size on a file locked it and sought first, and the threads sharing a file (every SPU worker appends to the SPU cache) waited on one another. Reads and writes now carry their offset, the position and the size are numbers the core keeps, and an append takes its place at the end with one atomic add. An older frontend, or a platform where the frontend has none, gets the lock as before. `test_vfs_positional` reads at offsets and appends from four threads on one handle with a frontend of each kind, checks every byte and record, and that the v6 frontend's handle is never sought.
- The pad keeps the frontend's precision. Two losses a DualShock 3 does not have:
  - Every button was pressed or not: 255 or 0. A DualShock 3's buttons and triggers are pressure-sensitive, and a trigger or button the frontend reports as analog (RETRO_DEVICE_INDEX_ANALOG_BUTTON) now reaches the game as its pressure: half pressed is 128, where it was 255. A racing game's throttle on R2 was all or nothing.
  - A stick's 16 bits went through two halves of 255 steps, each halved again, truncating both times: pushed all the way left or up read 1, never 0, and the pad's value 0 could not be reached. They go to the pad's 8 bits in one step, rounded: 0 full left or up, 128 at rest, 255 full right or down.
  The conversion is a C89 module of its own (`libretro_pad_values.c`), which reads the frontend's answers where they are rather than from a buffer gathered first; `LibretroPadHandler::process` uses it in place of its own C++ and takes 110 ns a pad a frame where it took 114 (the best of seven runs each), while reading twelve pressures more. `test_pad_values` runs all 65536 stick positions and all 32767 pressures against exact rounding; `test_pad_handoff` checks a half-pressed R2, a button-only Cross and the stick's range through the handler - on the code before, R2 read 255, full left 1, and one of the 256 values was never reached.
- The RSX audio path's periods (`sys_rsxaudio`, for games that go around cellAudio) and the PS Move's update and time-outs (`cellGem`) go by the PS3's clock, which follows retro_run, as the rest of the game's time does: they stop while the frontend is paused and follow fast-forward. The RSX audio ring's timestamps are made from that clock directly, not from a host time converted. `test_guest_clock` checks at all three paces that such a timestamp is the timebase's value then, and that the clock stops through a pause. cellAudio's own periods stay on the host's clock, as they were while the movies were checked.
- Reading the frontend's buttons into the pads allocates nothing. Each retro_run made a map of the 24 buttons and stick directions for each pad and threw it away: 26 allocations a pad a frame. They are read into an array in place. `test_pad_handoff` counts the allocations of a thousand frames of input: 26000 before, none now.
- The files the core installs at start (the game patches, the settings database) are compared with what is on disk a piece at a time, not read whole into a buffer of their own first.
- Movies play again (Demon's Souls' title screen movie and the first of a new game played neither) with the PS3's clock following retro_run. Two faults in that clock:
  - Whenever retro_run came a little faster than the frame rate the core declares - a 60 Hz display with 59.94 declared is enough - the guest's clock was ahead of the host's, and a host time taken as the guest's came out as zero: the lag between the two was kept unsigned. Every timed wait of the game's with a deadline then ended at once, and VBlank and audio timestamps were wrong. The lag is signed; a deadline and the VBlank time read the guest's clock itself.
  - A sleep of the game's was waited out by the host's clock, so in a 4x fast-forward a 20 ms sleep took 81 ms of the game's time. Sleeps and lv2 timers wait at the pace retro_run comes.
  `test_guest_clock` now runs retro_run at the declared rate, a little faster and in fast-forward, and checks at each that a host time taken as the guest's is the guest's time then (all 240 were wrong before, by up to the whole uptime), that a deadline 50 ms away has 50 ms left, and that a 20 ms sleep takes 20 ms of the game's time. Not run with the game here: Demon's Souls' movies are the check.
- The LLVM built into the core builds where valgrind is not installed. - Music for games (cellMusicDecode: a game playing the user's music, and cellSearch and the media list overlay listing it) goes through libretro-common instead of FFmpeg: a track is found by its bytes, not its extension, and decoded by audio_transfer - MP3, AAC (MP4/M4A and ADTS), WMA, ATRAC3 and ATRAC3plus (.oma, .at3), WAVE, FLAC, Vorbis, Opus, AC-3 - folded to stereo and resampled to 48 kHz with libretro-common's sinc resampler; its title, artist, album, genre, track, disc and date are read by rtags; videos are listed by libretro-common's MP4, Matroska, MPEG program stream, AVI and ASF readers. The file is mapped where it lies, not opened through FFmpeg's I/O. CI plays files FFmpeg wrote - MP3 at 44.1 kHz, AAC, WMA2, FLAC 5.1, mono WAVE at 22.05 kHz, Vorbis at 32 kHz - and the sound is FFmpeg's, resampled as standalone RPCS3 resamples it: within 51 to 83 dB of it, mono at -3 dB on both sides and 5.1 folded as before; the tags are ffprobe's, and the codecs and lengths of the files and of six videos (MPEG-4 and AVC in MP4, AVC in Matroska, MPEG-1 and MPEG-2 program streams with MPEG audio or AC-3) are what cellSearch had from FFmpeg. Different from before: an MP3's length no longer counts its encoder padding (FFmpeg's estimate did); Vorbis, Opus and FLAC in Ogg have their tags listed (FFmpeg gave cellSearch none); the year of a date such as "2004-05-01" is listed, where only a bare year was. Not tried with a game yet.
- Video decoding for games (cellVdec: the movies and cutscenes in AVC, MPEG-2 and MPEG-4/DivX) goes through libretro-common's rh264, rmpeg1_video and rmpeg4_video instead of FFmpeg's decoders, and the pictures are converted for the game by libretro-common's YUV conversion instead of swscale. CI decodes streams FFmpeg encoded, with B pictures, and every picture is FFmpeg's - the same bytes in AVC, within one level in MPEG-2 and MPEG-4 - in display order, with the time stamps and user data of the access unit it came from and its picture type; B-skip and PB-skip drop the pictures they did; RGBA and ARGB come out within 3 levels of swscale's, UYVY the same. RGB is converted in the colour matrix the game asks for (BT.601 or BT.709), where swscale always used BT.601. MPEG-4's frame rate comes from the time between pictures, where FFmpeg's often fell back to 30. The decoded pictures go into buffers kept in a lock-free pool and reused, where a frame was allocated for every picture, and the alpha plane for RGBA output is gone. AVC decodes on one thread, about 80 pictures a second at 1080p on CI's machine. Not tried with a game yet.
- ATRAC3plus audio for games (cellAtracXdec: the music and voices of many PS3 games, and movie sound) is decoded by libretro-common's ratrac3p instead of FFmpeg's decoder. The sound is what it was: CI decodes streams of every channel configuration, mono to 7.1, with a different signal in each channel, and compares them with what the core's FFmpeg (8.1.1) path gave - within 7 millionths of full scale as floats, one step at 16 bits - with every channel in the place it was. A frame is decoded from where it lies in the game's memory, without copying it into the decoder's work memory first, and the decoder is made once for a stream and reset when the game starts it again, where FFmpeg's was set up again at every new sequence. Not tried with a game yet.
- Video post-processing for games (cellVpost: a decoded picture to RGBA for the screen) goes through libretro-common's YUV conversion and scaler instead of FFmpeg's swscale. The picture is converted in the colour matrix (BT.601 or BT.709) and range (full or broadcast) the game asks for, where swscale was always given BT.601 broadcast range. Scaled down, the picture is filtered with a windowed sinc instead of swscale's bilinear, which skipped samples: five times closer to a careful scaling of the same picture on CI's; scaled up it is bilinear, a little closer than before. The alpha the game asks for is put straight into each pixel, where a plane of it was allocated and filled for every picture, and a picture the size of the last takes no memory; one the size of the output is converted straight into the game's buffer. CI compares the conversion with what swscale wrote from the same picture (within 3 levels at one size, in both matrices) and the scaled pictures with a careful scaling of it, and counts the allocations of a repeated picture: none. Not tried with a game yet.
- The RSX blit engine's scaled and converting copies done in software (NV3089 with a scale, or between R5G6B5 and A8R8G8B8: some games' 2D blits, video and HUD layers) go through libretro-common's scaler instead of FFmpeg's swscale, the first of the core's uses of FFmpeg to move. Nearest-sample scaling picks the same samples as before; the "smooth" (first order hold) blits are now true bilinear, where swscale's fast bilinear stepped between columns. A8R8G8B8 to R5G6B5 takes each channel's top bits, where swscale went through YUV and shared colour between neighbouring pixels, which changed a noisy image's colours by up to half their range. The scaler and its buffers are kept from one copy to the next, so a copy the size of the last no longer sets up a new swscale context and allocates: it takes no memory. libretro-common is synced with RetroArch's. CI compares the copies with what swscale wrote from the same pixels (R5G6B5 to A8R8G8B8 the same bytes, nearest upscales the same colours, bilinear within 2 levels), checks every nearest pick and a short source slice, and counts the allocations of a repeated copy: none. Not tried with a game yet.
- JPEG headers for games (cellJpgDecReadHeader) are read right: the module walked a JPEG's segments by lengths read wrong (the high byte times 255, and from the second segment on the marker's own code in place of the length's low byte) and wanted a JFIF segment first, so it refused nearly every JPEG with CELL_JPGDEC_ERROR_HEADER - any with a quantization table before the frame header, which is how encoders write them, and every Exif file - and games could not decode them. Standalone RPCS3 has the same bug. The header is now found by the segments' real lengths, after any application segments (JFIF, Exif, Adobe), from any kind of frame (baseline, progressive, and the rest). CI reads the header of every test JPEG, with an Exif segment longer than 255 bytes, fill bytes and a progressive frame, and every file cut short before its frame header; the old walk refused all 16 test files. The component count and colour space reported stay as they were. Not tried with a game yet.

The Makefile's checks for installed Vulkan and GLEW and its message about what to install are gone, as is the unused MoltenVK project. CI checks that the Linux and macOS cores need no Vulkan library and the Windows core imports no vulkan-1.dll. Not tried with a game yet.

- JPEG decoding for games (cellJpgDec) writes each row straight into the game's buffer, in the format it asked for, instead of decoding the whole picture into memory of its own and copying it over, and takes its decoder from a pool of eight that finished decodes give back, instead of making one, with its planes and its picture, at every decode. Once the decoders have decoded an image of a size, decoding another no bigger takes no memory; the pool is lock-free and emptied when the emulation ends. Reading the header no longer copies the whole file into new memory first: a JPEG in the game's memory is read where it lies, a file into the pool's memory. CI decodes JPEGs in each layout and colour space games ask for and compares every byte with what the module wrote before, and counts the decoder's allocations: none after the first round, where the old way took five an image. Not tried with a game yet.

- Save states no longer go through a file: Save State has RPCS3 write the machine's state into memory the core keeps, and Load State boots from RetroArch's buffer through that same memory, instead of writing `<title>_libretro.SAVESTAT.zst` to disk and reading it back. A save copies the state once, into RetroArch's buffer; a load copies it once, out of it. The memory is kept for the session and reused by the next save, so it is not taken again each time. Not tried with a game yet.
- RPCN: dropping the connection (a failed login, a reconnect) no longer frees it under the reader and writer threads: it waits for both to have left it, which they do within 50 ms. Before, the connection could be freed while the reader was still in it. The two threads are told apart from it with atomics instead of a mutex each, and the packets to send go through a lock-free queue instead of a mutex-guarded list. The writer thread no longer ends for good after a failed send, which left later connections with nothing to send their packets. Not tried against the RPCN server yet.

RPCN reads on one thread and writes on another at the same time, which wolfSSL did through its "write dup"; libretro-common's client now has a duplex mode for this with no lock, where a key update the server asks for is answered by the writing side. The server's certificate is still not checked. The handshake waits on the socket for what it needs instead of spinning, for 10 seconds at most, and may now be TLS 1.3 where the server offers it. - Reset works for a game loaded from a disc image (`.iso`): it used to close the content with "The game could not be restarted", because stopping the emulator unmounts the image and the reset booted the game from it without mounting it again.
- Android x86_64 (buildbot): ffmpeg is built with its x86 assembly, as the buildbot's Android image now has nasm; it decodes the games' videos faster there.
- The `libretro-latest` release is gone: libretro's buildbot builds the core for every platform it had, and installs it through RetroArch's Online Updater, while the release had fallen behind. Test builds stay as artifacts of the CI workflow.
- Android: a game behind a `saf://` path, as the Play Store RetroArch gives for folders it was granted, is read through RetroArch's VFS for directories too: listing, stat, creating, removing, renaming and copying, not only opening files. That is what an unpacked game in such a folder needs. Ordinary paths are untouched. Not tried on a real SAF path by anyone yet.
- New option Disk Cache Size (1 GB by default, 5 GB, Wipe on Exit or Unlimited as before) for the games' cache on `dev_hdd1`: with a size RPCS3's own disk cache limit is used, deleting the caches used longest ago when a game is loaded and when it is closed; Wipe on Exit deletes all of it at both points (NNshi).
- The settings database in `GuiConfigs/config_database.dat` is replaced by the core's only when it is missing or carries an older `timestamp` than the core's; it was replaced whenever its bytes differed, so entries edited by hand did not stay (NNshi).
- New option GPU > Aspect Ratio, 16:9 (default) or 4:3, as RPCS3's own setting: with 4:3 a game with a native 4:3 mode renders for it, and the core tells RetroArch the picture is 4:3 (unless Stretch to Display Area names another ratio); the picture fills the frame, so Stretch to Display Area does not have to be set for it. Takes effect when the game is started (NNshi).
- Frame Pacing is an option again (Emulator clock by default, or RetroArch: one PS3 refresh per frame RetroArch shows). It had been removed on one tester's result, which he could not repeat (NNshi).
- Pause and Frame Advance with the Vulkan renderer: once RetroArch stops asking for frames, the game waits after the frame it is drawing, and each Frame Advance step lets it draw exactly one frame and shows that one, drawn with the input of that step. The game used to run on for a tenth of a second and a step let 4-6 frames through (NNshi).
- Sound after unpausing: the first frames after a pause handed RetroArch up to four frames' worth of sound at once, which with RetroArch's audio sync on made the frame rate drop and swing for seconds. A pause is no longer made up for (NNshi).
- Linux: the core no longer links libGL, libGLX and libX11, so it loads on a system without X11. It links libOpenGL for OpenGL itself, and the GLX and Xlib functions it shares RetroArch's context with on an X11 session are found at run time, in RetroArch's own libraries.
- VBlank Frequency has a new choice, From List: a game named in `vblank_unlock.txt` runs with a 120 Hz VBlank - shown at 60 frames a second when it is a 30 fps game, at 120 when it is a 60 fps one - and any other game stays at 60 Hz. The list ships with the core and is written to `system/rpcs3/` when it is not there; the core never overwrites it, so titles can be added. It comes from the RPCS3 wiki's list of VBlank-compatible games and NNshi's testing.
- Frame Pacing is removed, option and code: the game's frames are timed by RPCS3's own clock, as in standalone. The other choice, one VBlank per frame RetroArch shows, added input lag and was better in no case tested.
- Save Data Slot is removed: the game's save list is always shown in the picture. The core picks the first entry itself only when the list cannot be shown.
- Default Resolution's tooltip warns against using it to upscale; Resolution Scale is for that.

## October 2026

### Upstream

- Merged up to upstream RPCS3 build 20243 (v0.0.43), after builds 20147 and 20149. The core reports upstream's version and build number, with this repository's commit after it, and logs both at start.

### Picture

- Vulkan through RetroArch's own hardware context: the renderer draws on RetroArch's device and hands each frame over as an image, with no copy through system memory. Finished frames are handed over in order, each once, so the picture no longer judders against RetroArch's refresh. The context is kept across RetroArch's video driver rebuilds, and replaced images stay alive until RetroArch has moved on.
- Before the first picture the Vulkan frame is 720p at the Resolution Scale, so the compilation progress is drawn sharp.
- A game no longer holds RetroArch through its PPU compilation at boot.
- Output Scaling and Vulkan Frame Readback are no longer options. Frame Pacing defaults to the emulator's clock.
- macOS: Vulkan through MoltenVK, no OpenGL in the core.

### Sound and pads

- Surround sound: the Audio Format option (Stereo by default, Surround 5.1, Surround 7.1) is what the PS3 reports to games, and with 5.1 or 7.1 the channels go to RetroArch's multi-channel output.
- Rumble through RetroArch's rumble interface.
- Pads report a PlayStation 3 controller, as standalone's handlers do, and the sticks reach full diagonals.

### Games and files

- PKG files are installed without being started, into the configured dev_hdd0, and the `.rap` licenses next to a PKG are installed with it.
- RPCS3's game patches (`patch.yml`) and its settings database ship with the core; Database Settings Override says whether the database's per-game settings apply. They, and the in-game overlays' icons, are rewritten when their contents differ.
- Save data is picked from the game's own list, shown in the picture.
- Emulate BD-ROM Read Speed as a core option.

### Core options

- The options carry RPCS3's own names and sections, in the layout NNshi proposed: CPU, GPU, Scheduling, Network, Debug, Core. Each option does what it says; several that were never read are now connected.
- Options for Disable Blit Engine Upscaling, RPCS3's performance overlay and the Resolution Scale Threshold.
- VBlank NTSC Fixup on by default, as in RPCS3.
- PSN Status says where an RPCN account comes from.
- On big.LITTLE ARM CPUs the compiler threads default to the big cores, and only the efficiency cores are left out.

### Builds

- macOS cores for Apple Silicon and Intel, and Android x86_64 next to arm64-v8a.
- The Windows core is `rpcs3_libretro.dll`; Linux links curl in instead of depending on Debian's libcurl-gnutls.
- Recipes for libretro's buildbot: Linux, Windows (cross-built with llvm-mingw), Android and macOS.

## Late September 2026

### Picture

- Vulkan is the default renderer, and the renderer option picks the renderer.
- Resolution Scale works: the scaled picture is carried through to RetroArch on both render paths and its size is reported.
- RPCS3's in-game dialogs are on and see the controller, including those that open before the game's first frame.

- A flip that waits forever for an image is reported and got out of, and the log says where the frames stopped when the picture does.

### Sound

- RetroArch gets one frame of audio per retro_run, at the rate the game played it, and is no longer starved of audio.

### Games and files

- Disc images boot: the ISO reader is ported from upstream, the game is found through its PARAM.SFO or PS3_DISC.SFB, and redump keys are found by the ISO's name.

- Reset stops and boots the game the way unload and load do, and a game that restarts itself (exitspawn) keeps running.
- RPCS3's config and caches are under `system/rpcs3/`, and paths resolve the way standalone's do.
- Network options, with Winsock set up on Windows.

### Stability

- Closing content: the emulator finishes stopping before the disc goes away, the log writer thread is stopped in retro_deinit, and RPCS3's exception handlers are taken out on every unload on Windows.

- The Qt application, the standalone's input handlers and audio backends and the 7-Zip SDK are removed: the repository builds the core only.
