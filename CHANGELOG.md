# Changelog of the libretro core

What changed in the libretro core of this fork, newest first. Changes that come with a merge of upstream RPCS3 are in upstream's own history; a merge is noted here with the upstream build it brought in.

## Unreleased

- `atomic_t` is gone from `Emu/CPU` (CI checks it with the five directories before). The CPU thread code's counters, its list of suspend requests, its table of the 128 threads `suspend_all` pauses and the 128-bit word of their slots are `retro_atomic` words called directly; the slot word is the first user of libretro-common's 128-bit compare-and-swap. Taking and giving back a slot is now `Emu/CPU/cpu_slots.c` (C89), with a test of its own: four threads taking and giving back slots in bursts never hold one slot twice and leave none taken, and it fails when either compare-and-swap is turned into a plain store. The suspend counter is a 32-bit word now, so that the threads waiting for a pass to end wait on it with `retro_waitaddr`; it only ever goes up and is compared for equality, so it may wrap. Left: `cpu_thread::state`, an `atomic_bs_t` used by every thread in hundreds of places, and the lock around `suspend_all`; they get a pass of their own. Not run with a game.
- LLVM has no lock left in anything the core builds of it. `make check` goes through all 1,088 of its library sources for one, and through the objects in `libllvm.a` for a call to a mutex, a read-write lock, a condition or a once-flag of the system's; there is none on Linux x86-64, Linux ARM64 or Windows. What went this time: the signal handling (LLVM in the tree installs no signal handlers, removes no files when a signal arrives and prints no stack traces - it is a library in a frontend's process - so the two system files that did that under two locks and a critical section are not compiled); the promise and future the run-time linker waited on for every object it linked, though the answer was always there before the call returned (an allocation, a once-flag and a condition less per object); the once-flags of the jobserver client and the code-gen data, now `llvm::call_once`; and the locks around reports that tools ask for and a library never makes - pass timers, statistics, the time trace, instruction-selector coverage, the machine verifier's error output - which are simply gone, those reports being one thread's if they are ever turned on. Two cuts took whole parts out with their locks: `Process::Exit` no longer asks for a crash recovery context, and the one function that read profiles from files (llvm-profdata's) is gone from `InstrProf.cpp`, which was all that kept the profile readers and with them the entire DWARF reader in the core. 44 more files are not built (984 objects in the archive, from 1,030); the core is 1.3 MB smaller and compiles the same code.
- More of LLVM's locks are gone: the ones in its JIT engine, MCJIT and the run-time linker (`ExecutionEngine`, `MCJIT`, `RuntimeDyld`), a recursive mutex taken thirty-odd times on the way from a module to code. Each compiler has its own engine and uses it from one thread at a time, so nothing ever waited on them; they are removed, not replaced, and the engine's header says an engine is one thread's at a time. MCJIT also no longer puts itself on the debugger's list (the GDB JIT interface) as it is made - the core took it off again each time, since being on it copied every object loaded - so the two files behind that list, with its process-wide mutex, are not built. A build fix with it: the core's own files are now made again when a header of the tree's LLVM changes. They were not, because LLVM's headers come in as system headers, so after a patch that changes one of LLVM's classes an incremental build linked core files compiled against the class as it was. The first build after this one starts over once for that reason.
- LLVM builds faster: 636 of its files are no longer compiled (1,030 objects in the archive on Linux x86-64 where there were 1,658). They are files of LLVM's libraries that no link of the core takes anything from - the PDB and GSYM readers, the ORC JIT, ObjectYAML, the machine-code analyser, the inter-procedural, vectorizing, coroutine and instrumentation passes, most of the scalar passes - worked out from the objects each target's link pulls in, on Linux x86-64, Linux ARM64 (which needs 22 files x86-64 does not) and Windows x86-64, with everything of Support, TargetParser, Demangle and the execution engine kept either way. The core is the same size and compiles the same code; the files stay in the tree and are listed in `rpcs3/libretro/make/llvm/unlinked.txt`, which `gen.py` reads. macOS could not be linked here: if its link asks for one of them, the error names it and the file's line is taken out of `unlinked.txt` and put back in `llvm.mk`. The archive is also made again when the lists change.
- LLVM's locks are being taken out of the copy in the tree (`3rdparty/llvm`), the ones every recompiler thread shares first. The pass registry had a reader-writer lock taken for every pass looked up and every pass registered; the statics LLVM makes on first use (`ManagedStatic`) were all made under one recursive mutex; `llvm::call_once` was `std::call_once`; the symbols and libraries the JIT's linker falls back on (`DynamicLibrary`) were searched under a mutex for every name it had to look up; the fatal-error handlers were read under two more. None is left in those files: the registry is two tables of pointers that are only added to, a slot taken with one compare-and-swap; a static and a once-flag are claimed with one, and a thread that finds one being made by another yields until it is made (there is nothing it could go on with, as under the lock); the libraries are slots taken the same way and the symbols a list added to at its head; a handler and its data are two words. All of it calls libretro-common's `retro_atomic`, which LLVM's files are now compiled with on their include path. `make check` runs the first compiles of a process on four threads at once, then the registry and the symbol list from four threads registering and looking up together, and fails if a lock comes back into one of those files. The locks left are in LLVM's JIT engine and linker, which each compiler has to itself, and in parts the core does not run (timers, statistics, the DWARF reader); they go next.
- An SPU function whose compiled object is in the cache is loaded without its LLVM module being built again. The object is kept under a name made from the module, so on every boot each function's module was built, written out as bitcode and hashed just to find an object that was already there - most of the time a cached function took. A note is now kept in the pack beside each object, under a name made from what the module is built from (the SPU code, every setting the recompiler reads, the CPU, and the build of the recompiler): it says which object it is and which outside names the object links to. A function with a note gets its object and those names' places and nothing else; in the JIT test 200 cached functions load in 26 ms where they took 166 ms. A function without a usable note - a new build, a changed setting, an object not noted yet - goes the old way, finds its object by its module as before, and leaves the note for next time, so existing caches are kept and fill in their notes on the first boot. The places of the host functions compiled code calls are remembered by name as modules name them (`Emu/CPU/jit_host_symbols.c`, lock-free): a fresh process has none, so the first function to call each is built the old way, and a name ever seen with two addresses is not answered for. `make check` fails if the recompiler reads a setting that is not part of a note's name. Not run with a game.
- `atomic_t` is gone from two more directories, `Emu/Io` and `Input` (CI now also fails if one of the finished directories includes `util/atomic.hpp` again): the interception flags and the active mouse-and-keyboard device, the camera and music handlers' states, the pad thread's flags and its pointer, the home menu flag, and the PS Move tracker's two per-worker words, whose waits go through libretro-common's `retro_waitaddr` (as the file system's do) instead of `atomic_t`'s own wait machinery. The counter an overlay message is queued with (`queue_message`'s `refs`) is a `std::shared_ptr<retro_atomic_int_t>` now, for the pad thread's and everybody else's. Two were not atomics at all and are plain now or gone: the pad thread's copy of the pad mode, read and written by that thread only, and the mouse config's `reload_requested`, set on every save and never read.
- The core is 19 MB smaller (Linux x86-64: 108.0 MB to 88.9 MB before stripping; code from 59.7 MB to 46.4 MB) and compiles exactly the same code. The PPU and SPU recompilers run five optimisation passes of LLVM's, but set them up through LLVM's `PassBuilder`, which can build any pipeline and so refers to every pass LLVM has: the vectorizers, the inliner, OpenMP, coroutines, the sanitizers' instrumentation, an assembly parser. All of it was linked into the core and never run. The recompilers now register just the analyses their passes ask for (`jit_register_analyses`, `Utilities/JITLLVM.cpp`), set up as `PassBuilder` set them up; 321 of LLVM's 1,261 objects in the core are gone from it. CI's JIT test prints a checksum of the 200 SPU functions it compiles, and it is the same before and after (`8fd6a75f` on the machine it was run on); compile time is unchanged within noise. LLVM's objects are also rebuilt now when a header of LLVM's changes, not only their own source: the tree's LLVM is the core's to change, and the Makefile did not track its headers. Not tried with a game yet.
- Two tests failed on a busy machine and no longer do: `test_lf_sig_table` and `test_guest_page_locks` each check at the end that their racing threads really met (a lookup found an item in the table; the game left notes for the renderer), and with something else using both processors one side could finish all its rounds before the other had run - 16 of 40 runs of the page-locks test failed that way beside a compiler job. The side that would run ahead now waits for the other until they have met often enough. The page-locks test also has a watchdog: with its locking broken it could wait for ever instead of failing.
- LLVM's sources are in the repository now (`3rdparty/llvm/llvm`), not a submodule fetched from llvm-project: the files of LLVM 22.1.8 the core is built from, with the headers and TableGen inputs they need - about 4,600 files, 96 MB - and nothing else of LLVM (no CMake, tests, tools or other targets). They are the core's own to change from here on. The Makefile builds them as before, without fetching anything. The CMake build's `BUILD_LLVM`, which built the submodule with LLVM's own CMake, now has the Makefile build the same sources (`make llvm`), so the Windows cross build, the Android build and the buildbot's macOS build get the LLVM the Makefile build gets; they need `make` on the build machine. The macOS script still builds clang, its compiler, from LLVM's release, which it now fetches itself. Checked here: every LLVM source of the Linux x86-64, Linux ARM64 and Windows x86-64 builds finds all its headers in the tree, TableGen writes the same tables from it as from the submodule, and a small CMake project builds, links and runs against it through `BUILD_LLVM` on Linux. Not built here: Windows, Android or macOS through CMake, and macOS at all. Builds that use an installed LLVM (`BUILD_LLVM=OFF`, `SYSTEM_LLVM=1`) are unchanged and will not get changes made to the tree's LLVM.
- Compiled PPU and SPU code is no longer kept twice in memory (Linux, Android and other ELF hosts). LLVM's MCJIT registers every object it loads with the debugger interface, and for that makes a second copy of the whole object, allocates an entry for it and keeps both until the compiler that loaded it is closed - which undid the pack's lending of objects with no copy - all under one lock shared by every compiling thread. The core takes its compilers off that list as they are made; nothing reads it unless a debugger is attached to the frontend. The copy and what it held are gone; the time to load 200 small SPU objects in CI did not change measurably (about 155 ms before and after), so this is memory and a shared lock, not a speed-up that was measured. Windows and macOS never made the copy. CI checks that nothing is on the debugger's list after code is compiled and after it is loaded from the pack; before the change both checks fail.
- libretro-common's `retro_atomic.h` synced from RetroArch: it has a 128-bit word now (`retro_atomic_128_t`: load, store, exchange and compare-and-swap of two 64-bit words as one, on x86-64 and AArch64). That is what the core's 128-bit `atomic_t`s - memory reservations' waiters, the shared pointers' word, a few sync structures - move to as `atomic_t` is taken out. Nothing in the core uses it yet.
- RPCS3's own atomic type (`atomic_t`) is being replaced by direct calls to libretro-common's `retro_atomic`, a directory at a time, so that its header and what is left of its machinery can be deleted; CI lists the directories that are done and fails if one gets an `atomic_t` back. First: the package installer's counters, the licence keys, the ISO key status, the TAR extractor's two positions and the audio mute. The licence keys a game registers were sixteen 128-bit atomics with a count beside them, written inside a retry loop on the count; they are one lock-free record now, read whole and changed whole, and a savestate has them byte for byte as before (CI compares, registers keys from four threads at once, and checks that sixteen protected files open at once and not a seventeenth).
- sys_ppu_thread_get_priority no longer takes the scheduler's lock. It took the reader lock to read one word, the priority, while the calling thread was not suspended; it now reads the word between two looks at the caller's own state and takes it if the thread was not suspended at either. Asking whether the scheduler is ready (once for every PPU thread that starts) reads a count kept beside the list instead of locking to look at the list. These were the last readers of that lock outside the debugger's thread view. The lock itself stays: every sleep and wake-up changes the run queue, the deadlines and the count of threads owed a suspend together, and there is no test of the scheduler in CI to rebuild it against. Covered by a source check. Not tried with a game yet.
- A raw SPU raising an interrupt no longer takes the lock over all kernel object IDs (`spu_int_ctrl_t::set`): every write to an interrupt mailbox, and every stop, of a raw SPU with interrupts enabled took the reader lock that all ID creation and destruction takes, to look at the interrupt tag and its handler. The SPU thread now counts itself in on the tag's own ID, which keeps the tag, the handler it points at and that handler's thread until the wake-up is done; destroying the tag and establishing a handler on it let a thread that is in there finish first, as event ports do. The interrupt control keeps the tag's ID and address beside the tag for this, so that an ID that went to another tag is told apart. Covered by a source check only: no test here builds a raw SPU with an interrupt thread. Not tried with a game yet.
- sys_memory_free no longer takes the lock over all kernel object IDs. It took the reader lock for the one step that gives the freed size back to its memory container, to keep the container from being destroyed meanwhile - which cannot happen: a container is only destroyed when its count is zero, checked and filled in one compare-and-swap, and the count is not zero until that step is done. Every other place that gives memory back to a container already did so without the lock. Two interlocked steps fewer on the word all threads share, for every free. Covered by a source check.
- The texture cache's lock is gone (Vulkan and OpenGL). Every texture lookup for a draw, every upload, blit, flush and invalidation took it - shared or exclusive, with an upgrade in the middle of an upload - and since the changes below only the renderer was ever taking it. What it still did was tell the cache that it was being entered from within itself: when the cache's own allocation runs out of video memory, the eviction and trimming that follow must not run inside the operation that asked. A plain count of how deep the renderer is inside does that now, with no interlocked step. CI's source check fails if the lock, or a second thread's way into the cache, comes back. Not tried with a game yet, and not measured: the saving is two to four interlocked steps a texture lookup.
- The last two ways into the texture cache from a thread other than the renderer are closed, and the code the renderer's hand-over made dead is removed. A thread that unmapped guest memory while an earlier unmap was still waiting, or mapped memory over one, did the renderer's invalidation itself (on OpenGL that meant GL calls from a thread with no context); it now asks the renderer and waits, the same way a fault is handed over - the renderer answers from where it is paused for the unmap. A fault that arrives while the renderer is ending no longer falls back to the faulting thread entering the cache: the renderer takes the fault handler down, answers what is waiting, and a thread that comes after is told to try its access again. That also replaces a 10 ms sleep the renderer took at its end in the hope that all waiting threads had arrived. Gone with this: the path by which a faulting thread stopped the Vulkan renderer and flushed on the second command buffer itself, and the OpenGL renderer's queue of flush requests with its lock. One case can now wait where it did not: mapping memory over a waiting unmap, if the renderer is at that moment taking a range lock inside the range being mapped. Not tried with a game yet.
- Fixed a CI test that failed on runners with more cores (`test_gem_shared`, "torn == 0"): its three reader threads check that a sphere's position goes with its number, and the record the tracker starts with is all zeroes - whole, but not of that shape. Where the readers got going before the first result was published they counted the starting record as torn. A first result is now published before the readers start. Nothing was wrong in cellGem or in the record it publishes through; giving the readers a 50 ms head start made the old test fail every time and leaves the new one passing.
- Only the renderer enters the texture cache now (Vulkan and OpenGL). A thread that faulted on memory the cache has locked, and could not deal with it alone (the change below), went into the cache itself, under the cache's lock and beside the renderer: it searched the cache, marked sections, and for memory that had to be written back first then asked the renderer to stop and did the flush on a second command buffer. It now hands the fault to the renderer and waits: it posts a record from its own stack with one compare-and-swap (`Emu/RSX/Common/guest_faults.c`, C89), and the renderer, at the points where it already looked for flush requests, handles the fault exactly as it handles one of its own and wakes the thread. Whether a fault is the cache's at all is read from the table of locked pages, with no lock, so faults that are somebody else's never go near the renderer. A renderer that another thread has paused still answers, since the thread that paused it may be the one waiting; one that is waiting for the offloader thread is told the offloader's range, as before, but before the offloader touches the cache rather than after. When the renderer ends it answers what is waiting and closes, and a fault after that is handled the old way. The cache's lock is still in the code but no two threads meet on it any more; taking it out is the next step. For the faults that needed a flush nothing is slower - they waited for the renderer before; the few that did not now wait for it to reach its next check. CI has four threads posting faults while a fifth answers and then closes under them: every fault gets its own answer, each thread's in order, and no thread is left waiting; a close that forgets a waiting fault, an answer that wakes nobody, or a post after the close each hang or fail the test. Not tried with a game yet.
- A game thread that writes over a texture no longer takes the texture cache's lock (Vulkan). The renderer write-protects the guest memory its textures were read from, and a game writing there faults: the faulting thread took the cache's lock, searched it, and waited for the renderer whenever it held the lock, which it does for as long as it uploads. For the common case - the page holds only textures the renderer read from, nothing it has to write back - the thread now makes the page writable itself, leaves a note and goes on; the renderer throws the stale textures away when it next enters the cache. A table with one word per 4 KiB page says how each page is protected (`Emu/RSX/Common/guest_page_locks.c`, C89). The two sides cannot undo each other: a lock is counted in the table before its protection is applied; a thread takes the page in hand with one compare-and-swap, which fails if anything on it needs flushing or the occlusion-query code holds it; and whoever protects a page waits for a thread that has it in hand, a few instructions. The thread also no longer takes the sampler lock, which the renderer holds while it loads a draw's textures; it sets a flag the renderer takes there. Still the old way: pages with something to flush, reads, the renderer's own faults, and hosts whose pages are larger than 4 KiB; the cache's lock itself is still there for those, and going without it is the next step. CI runs a model of the two sides - a renderer locking, unlocking and collecting notes on six pages against three threads writing to them - and checks that no page is ever writable while a lock on it is in force with no note left, also under ThreadSanitizer; without the wait, or with a thread that ignores a page it must not take, the test fails. Not tried with a game yet.
- Resolving a PS3 path to a host path takes no lock. Every open, stat and directory listing a game makes looked the path up in the mount table under a reader lock that all threads shared. The table is now a tree that is never changed once it is in use: mounting and unmounting, which happen at boot and when a device comes or goes, copy it, change the copy and swap it in, and a lookup walks whichever tree was current when it started. Replaced trees are kept until the emulator stops (a few dozen small ones over a session), so a lookup never walks freed memory. CI has three threads resolving paths while another mounts and unmounts a device two thousand times: a path on a mount that stays always resolves to the same place, and a path on the one that comes and goes only ever to one of its two right answers; changing the tree in place instead crashes the test every run. One thread alone is neither faster nor slower (about 250 ns either way - the time goes into building the strings, not the lock); the gain is that threads no longer share a lock here. Not tried with a game yet.
- The core no longer makes two folders that it never put anything in: `captures` (RSX frame captures, which only standalone RPCS3's window can ask for) and `cache/shaderlog` (written only with shader logging on, which the core has no option for; the folder is still made if a config file turns that on). `sounds` stays: it is where a user can put replacement sounds for the overlays.
- The core keeps everything in `system/parallel-ps3/` instead of `system/rpcs3/`: the firmware (`PS3UPDAT.PUP` goes there, or straight into `system/`, and `dev_flash` is installed there), the emulated drives with installed games, saves and trophies (`dev_hdd0`), the disc keys (`data/redump/`), its config (config.yml, vfs.yml, the patches and the settings database), its caches (compiled PPU and SPU code, shaders) and `rpcs3_detailed.log`. `system/rpcs3/` is the RPCS3 core's folder, and the two cores sharing it wrote over each other's config and log and cannot read each other's caches: the RPCS3 core deleted this core's shader pack at every start. Nothing is taken over from the old folder and nothing in it is touched. To keep what is there, copy `PS3UPDAT.PUP`, `dev_flash`, `dev_hdd0` and `data` from `system/rpcs3/` into `system/parallel-ps3/` before the first start; without that the core asks for the firmware again and starts with no saves or installed games. The caches are not worth copying: each game compiles its code and shaders again at its first start.
- The core no longer writes an `Icons` folder. The pictures of the in-game dialogs, the on-screen keyboard, the trophy and friends overlays and the home menu were written out of the core into `Icons/ui/` at every start so that the overlays could read them back as files; they are decoded from where they lie in the core now. CI loads one with no such folder present and checks that none appears.
- The last single-object lookups under the lock over all IDs are converted: the five in the peer-to-peer socket code and cellAudio's hold on a game's audio memory. No call that works on one kernel object by its ID takes that lock any more; what still does are the calls that walk every object of a kind, creating and destroying objects, and savestates. Not tried with a game yet.
- Fixed, from the thread change two entries below, before any release had it: a thread that exits settles who joins it and wakes that thread while holding the lock over all IDs, which used to keep a join on it from being half done at that moment. Once joins stopped taking that lock, an exit could wake a joiner that had named itself but not yet gone to sleep, and the joiner then slept with nobody left to wake it. The exiting thread now lets the calls that are inside on its ID finish, and keeps others out, for as long as it held the lock against them (idm::close).
- sys_net_bnet_poll and sys_net_bnet_select no longer take the lock over all IDs for the time they look at their sockets: the thread counts itself in on each socket it was given, which keeps that socket from being closed until the call has looked at it and queued itself on it, as the lock did for every socket at once. This removes two of the shared locks that were left. Not tried with a game yet.
- Sockets, threads and memory no longer take the lock over all kernel object IDs for their per-object calls: the thirteen sys_net calls that work on one socket (accept, bind, connect, the get and set calls, listen, recvfrom, sendto, sendmsg, shutdown), joining, detaching, renaming, starting a thread and reading or setting its priority, mapping and unmapping shared memory, memory containers, sys_vm's two block calls and the SPU thread lookup count themselves in on their own object instead (idm::check_entered, idm::get_entered), as event ports do since the change below. poll and select, which look at many sockets at once, and the calls that walk every object of a kind still take the lock. Not tried with a game yet.
- Event ports, event queues and timers no longer take the lock over all kernel object IDs. sys_event_port_send is the call behind most wake-ups in a game - audio, pad, vblank, timers and thread joins all end in it - and every send took the reader lock that every other kernel call also takes. It now counts itself in on the port's own word and out again: two interlocked steps, as the lock took, on a word no other object shares. That one count keeps the port alive and its queue connected, so nothing is pinned and no reference is counted; connecting and disconnecting a port, which change the queue the send reads, let the sends that are in there finish first (idm::close), and every way of removing an ID now does the same. One thread, measured in CI: 19.8 ns under the reader lock, 16.5 ns counted in; and for a lookup that keeps the object (receive from a queue, wait on a condition) 51 ns under the lock, 28 ns counted in (42 ns before this change). sys_event_queue_receive, _tryreceive and _drain and the five timer calls are converted the same way. CI has four threads reading ports' queues while another connects, disconnects, removes and recreates them: no thread is inside when the queue changes or once the port is gone; with either wait taken out, the test fails every run. Not tried with a game yet.
- Lightweight condition variables no longer take the lock over all kernel object IDs: _sys_lwcond_queue_wait, _signal and _signal_all find the lwcond with no lock. These calls name a second object, the lwmutex, and signal can name a thread: both were used through bare pointers that only the lock over all IDs kept alive, and are kept with references now. A wait counts the thread among the lwmutex's waiters and a signal can move a woken thread into the lwmutex's queue - what a destroy of the lwmutex asks about - so the lwmutex is counted in on as well (idm::enter), and always before any object's own lock is taken, so that a thread waiting for a destroy to decide never holds a lock that a thread the destroy waits for needs. CI has four threads counting themselves in on a lwcond and a lwmutex at once while another destroys and recreates both kinds in turn: neither destroy succeeds on an object with such a waiter, and the test ends, which is the check that nobody waits on anybody. Not tried with a game yet.
- Reader-writer locks no longer take the lock over all kernel object IDs: sys_rwlock_rlock, _tryrlock, _wlock and _trywlock, which take the lock or wait for it, count themselves in on the ID (idm::get_entered) so that a destroy sees them; _runlock and _wunlock only keep a reference. And the lock-free lookup that keeps the object is now faster than the locked one it replaces, not only free of the shared lock: with the object pinned, its reference is one increment, where loading the ID's pointer was three interlocked steps. One thread, measured in CI: 51 ns under the reader lock, 26 ns kept with a reference, 42 ns kept and counted in (before this change 49 and 64 ns). That speeds up the mutex, semaphore, event flag, lightweight mutex and condition variable paths of the changes below as well. Not tried with a game yet.
- Condition variables no longer take the lock over all kernel object IDs: sys_cond_wait, _signal, _signal_all and _signal_to find the condition with no lock. Signalling makes no thread wait on the condition, which is all sys_cond_destroy asks about, so it only keeps a reference; a thread that goes on to wait counts itself in on the ID first, as lightweight mutexes do, so a destroy waits those few instructions and finds it in the queue. Two helpers make the remaining kernel objects a one-line change each: idm::get_held and idm::get_entered do what idm::get did, without the lock, for code that makes no waiter and for code that may. sys_cond_create takes its mutex with the lookup that cannot return a new object for a destroyed ID. CI checks that the helpers find what the locked lookup finds and leave nothing a destroy would wait for, and runs the queue-against-destroy test through idm::get_entered. Not tried with a game yet.
- Lightweight mutexes no longer take the lock over all kernel object IDs: _sys_lwmutex_lock, _trylock, _unlock and _unlock2 find the lwmutex with no lock. These are the calls behind every contended sys_lwmutex in a game. Taking a lwmutex that was just given up, and giving one up that nobody waits for, count no reference either. A thread that goes on to wait is kept safe from a destroy in a new way that leaves the waiting code exactly as it was, with nothing to undo: it counts itself in on the ID before it looks whether the ID still names the lwmutex (idm::enter), and a destroy that asks about waiters marks the ID, lets the threads that are counted in finish, and only then looks at the queue. That wait is for this one ID, a few instructions long, and only when a destroy and a wait on the same lwmutex meet. CI has four threads putting themselves in the queue by ID while another destroys and recreates the lwmutexes; with a destroy that does not wait, or a thread that enters while a destroy is deciding, the test fails every run. Not tried with a game yet.
- Event flags no longer take the lock over all kernel object IDs: waiting on, trying, setting, clearing, cancelling and reading an event flag by its ID find it with no lock, as mutexes and semaphores do. Taking bits that are there, and setting bits that are set already, count no reference either. A thread that goes on to wait queues itself under the flag's own lock and then asks whether the ID still names the flag; sys_event_flag_destroy, which refuses while a thread waits, marks the ID before it looks at the queue - so either the destroy saw the thread and failed, or the thread leaves the queue again and reports that there is no such flag. sys_event_flag_set and _cancel took their reference with the lookup that could return a new object for a destroyed ID (see the semaphore change below); they use idm::hold now. CI has four threads queueing themselves by ID while another destroys and recreates the flags; without the second look the test fails every run. A check in the same test that failed about once in forty runs is fixed: after file reads are blocked it looked at a counter that may still blink by design (a reader counts itself in before it sees the handle is away, and out again without reading); it now counts the readers that are really reading. Not tried with a game yet.
- Semaphores no longer take the lock over all kernel object IDs: waiting on, trying, posting to and reading a semaphore by its ID (sys_semaphore_wait, _trywait, _post, _get_value) find it with no lock, as locking a mutex does since the change below. Taking or adding a count that makes no waiter needs nothing more. A thread that goes on to wait makes itself a waiter under the semaphore's own lock and then asks whether the ID still names the semaphore; sys_semaphore_destroy, which refuses while there are waiters, marks the ID before it looks for them - so either the destroy saw the waiter and failed, or the thread is no waiter after all and reports that there is no such semaphore. Also fixed on the way, for mutexes too: a thread about to sleep took its counted reference with a lookup that reads an ID's key and then its object, and if the ID was destroyed and its place given to a new object between the two, the thread got the new object for an ID that no longer existed. The reference is now taken while the object is pinned (idm::hold). CI has four threads becoming waiters by ID while another destroys and recreates the semaphores: no destroy succeeds on a semaphore a thread has been told it waits on; without the second look, or with the old lookup, the test fails. Not tried with a game yet.
- ATRAC3plus sound is closer to what FFmpeg's decoder gave: the decoder's seven quantiser step sizes were exact ratios (63/3, 63/5 and so on), and FFmpeg's output is up to 4 parts in 100000 off that for five of them, the same on three games' streams. The steps are now the ones fitted to FFmpeg's output. CI's worst float difference from FFmpeg drops from 6.6e-7 to 2.1e-7 on the channel-configuration streams (the 32-bit one from 1419 steps to 448), and on the game frames from 4.6e-5 to 7.7e-7 (Tekken Tag Tournament 2 music) and 1.5e-7 to 3.3e-9 (Tekken 5: Dark Resurrection); the test's limits are tightened to match, and the old steps fail them. This closes the 90 dB gap noted below. The difference was not audible.
- Fixed: music stopping in the middle of a fight in Tekken Tag Tournament 2, and a stage with no music in Tekken 5: Dark Resurrection. Both games close their music decoder at the first ATRAC3plus frame it refuses, and it refused frames where a tone's frequency has no room left above the one before it (it is already at the top of the range): the stream still carries one bit for the next tone there, the decoder (libretro-common's ratrac3p) read none, and the rest of the frame was read one bit early. These two frames match FFmpeg's to about 90 dB, where the other test streams reach 109 dB and more: that gap was there before and does not come from this change; it is being looked at. Not tried with the games yet.
- Fixed: Tekken Tag Tournament 2 stayed on a white screen instead of reaching the Namco logo. Its opening movies carry 5.1 ATRAC3plus sound, and the decoder (libretro-common's ratrac3p) refused every frame of it, so the movie player never got any audio and waited forever. In a stereo block whose second channel takes all of its tone bands from the first, the stream still carries the second channel's tone section; the decoder skipped it and so ended the block six bits early. With one block in a frame nothing follows, which is why stereo streams played; with the four blocks of 5.1 the next block was read from the wrong place. Any multichannel stream built this way was affected. CI decodes eight frames of that movie's sound, taken from a bug report's log, and compares them with FFmpeg's on all six channels, each in the place the game expects; the old decoder refuses all eight. Not tried with the game yet.
- For a bug report: when the ATRAC3plus decoder cannot read a frame a game hands it, the first eight such frames are written whole into the detailed log, with the channel configuration and frame size. Nothing is written when the log is off. - Locking and unlocking a mutex no longer take the lock over all kernel object IDs. Every syscall that names a kernel object by ID - a mutex, a condition variable, an event queue, a semaphore - looked it up under one reader lock shared by all threads and all object types, so every PPU thread wrote to the same word on nearly every syscall. This is the start of doing without it, module by module; `sys_mutex_lock`, `sys_mutex_trylock` and `sys_mutex_unlock` are the first. A thread now finds the object by announcing it in a hazard cell of its own (`idm::pin`, `Utilities/lf_hazard.c`, C89): no lock, no reference counted, and whoever removes an ID waits until no cell holds its object before the object can be freed. What the lock also guaranteed - that a mutex cannot be destroyed between being found and being locked - is kept by a mark `sys_mutex_destroy` puts on the ID while it checks that the mutex has no owner: a thread that has just become the owner asks whether the ID still names the mutex (`idm::still_named`), waits if a destroy is deciding, and if the ID is gone gives the mutex up and reports that there is no such mutex. Looking an ID up costs one thread 7.6 ns instead of 13.4, and threads no longer contend for it. The other kernel objects still use the reader lock. Covered by `test_lf_hazard`, `test_vfs_positional` (four threads locking mutexes by ID while a fifth destroys and recreates them) and a source check.
- Finding the buffer that mirrors a stretch of guest memory, and copying through it, take no lock (Vulkan). Texture uploads that go through the GPU ask for the DMA mapping of their source every time, and `map_dma` took the pool's mutex exclusively for each of them, mapped already or not; loads and flushes took it shared. Readers now look in a table with one entry per 64 KiB of guest memory (`Emu/RSX/Common/dma_views.c`, C89) that points at an unchanging description of the buffer: an existing mapping is found with one load and two compares, and a load or flush copies straight through it. Only making, growing or unmapping a mapping takes the mutex, and then brings the table up to date. A buffer that is replaced is handed to the deferred deletion with its description and still mapped, so a reader that found it a moment earlier can finish; buffers are also left mapped from the start rather than unmapped after the first fill and mapped again on first use. The two error messages for a transfer over unmapped memory are gone with the logging. Covered by `test_dma_views` (lookups, copies in both directions, ranges over two buffers, replacement under readers; also under ThreadSanitizer) and a source check.
- Mapping guest memory, and a fault the occlusion-query code is asked about, take no lock when there is nothing to do. Every memory map took a reader lock on the renderer's task mutex to see whether an unmap was still waiting to be handled - almost never - and every fault the texture cache did not take went on to the occlusion-query (ZCULL) code, which took a reader lock and searched a map for the page - almost never there. Each is now one load of a flag or a count kept beside the data, set under the same mutex as the data and before anything that could cause the notification or the fault; only when there is something to do is the mutex taken, exclusively. The renderer's own check of the pending unmap, which read a field of the range through `atomic_storage`, reads the same flag. Covered by a source check.
- What the Vulkan renderer is done with is disposed of and deleted with no lock. Every image, view, buffer or sampler the renderer lets go of is kept until the GPU has finished the commands that used it: disposing of one took a lock and appended to a vector in a list of scopes, and the driver thread, on every completed submission, took the same lock - shared, then upgraded - to cut the finished scopes out. Disposing is now a compare-and-swap push of a record onto a list; the driver thread takes the whole list in one exchange, puts it behind what it kept from last time and deletes what is due, in the order it was disposed of. Records come from and go back to a lock-free pool, so disposing of an object allocates nothing once the pool has filled (it grew a vector before), and a disposable carries a plain function pointer instead of a `std::function`. Holding the current event's objects for one more event (asynchronous texture streaming) is a mark on the event, which now also covers what is disposed of later in that event. Covered by `test_shader_corpus` (order, timing, a held event, and four threads disposing while a fifth completes events) and a source check.
- The Vulkan framebuffer cache is looked up with no lock. Every change of render target, and every overlay or post-process pass, looked its framebuffer up under a reader lock, in a hash map of vectors, comparing against each framebuffer's attachment views; a miss upgraded the lock. The cache is now a lock-free table (`Utilities/lf_sig_table.c`, C89) in memory of the core's own: a framebuffer is known by its size and by its attachments' images and formats, a copy of which the table holds, so a lookup is a walk of the slots' words that writes nothing and never touches a framebuffer another thread may be removing. Removing (unused for two frames, or made of an image that is going) marks a slot while it asks about it - the framebuffer is still found meanwhile - and empties it before the framebuffer is deleted; only two removals at once wait for each other. At most 1024 framebuffers are kept at a time (there was no limit). Measured against a stand-in for the old shape (not the old code itself), a lookup is 9 ns instead of 18 with 4 framebuffers, 17 instead of 18 with 16, and level at 64. The key's upper bits, which were left unset, are now defined. Covered by `test_lf_sig_table` (four threads adding, finding and sweeping their own while two look up everybody's, and one slot with two things taking turns in it; also under ThreadSanitizer) and a source check.
- The Vulkan texture cache's pool of spare images takes no lock. An image the GPU is done with is kept for reuse; putting one in took a lock, and every search for one - each time a texture or a temporary image is created - took a reader lock and then upgraded it, and walked the whole pool under it. The pool is now a lock-free one (`Utilities/lf_item_pool.c`, C89): a slot's key word is the image's key, a search is one plain load per slot - over about as many slots as there are images - and writes nothing until it finds a match, which it claims with a compare-and-swap; the count and memory total are added up when asked for, once a frame, instead of being kept on every put and take, and closing the pool on shutdown needs no lock either. Measured against a stand-in for the old shape (lock, upgrade, walk, erase - not the old code itself) a search that finds nothing costs 1 ns instead of 16 with the pool empty and 6 instead of 30 with 8 images in it, and taking an image and putting one back 31 ns instead of 45. Trimming the pool at the end of a frame still drops the older half. Covered by `test_lf_item_pool` (four threads putting and taking while a fifth trims, and closing the pool while threads put; also under ThreadSanitizer) and a source check.
- The Vulkan shader interpreter's caches are read and added to with no lock. Looking up the interpreter program for a draw took a reader lock whenever the draw's state differed from the last one's, as did finding the interpreter's two shaders, and the pipeline compiler's thread took the same lock to hand over each program it finished - so the renderer waited for it. The three caches are now lock-free maps: a program is made whole and then published with one exchange, and one that is replaced (an interpreter variant first served by a compatible program, then by its own) is kept until the interpreter is destroyed, so the program the renderer is drawing with never goes away under it and is held as a plain pointer rather than a counted one. A cache miss is no longer timed with the wall clock and logged. Covered by `test_shader_corpus` (six threads giving the same keys programs at once: none lost, none kept twice) and a source check in the library tests.
- Taking a Vulkan descriptor subpool takes no lock, and two threads can no longer take the same one. When a descriptor pool's current subpool is used up the next free one was looked for under a reader lock - and marked busy under that same shared lock, so two threads looking at once could both take it. A subpool is taken now by swapping its busy flag from 0 to 1 with a compare-and-swap and given back, once it has been reset, by storing 0; the subpools are a fixed array (256) with an atomic count, a new one put in a slot of its own. One reader lock and two exclusive ones gone. Not run on a GPU beyond the software driver the tests use.
- Polling a Vulkan command buffer takes no lock. `poke`, `wait` and `flush` of a command buffer chunk each took a reader lock - `poke` for every buffer of a chain whenever the next one is taken, and for the swap buffer every frame - to guard the one thing done when a submission is seen finished: the fence reset, the event completed, the buffer marked no longer pending. That is done once now by whichever thread claims it with a compare-and-swap, and a thread that comes meanwhile goes on without waiting; whether a buffer is pending is an atomic flag read with no lock. Three reader locks gone. Not run on a GPU beyond the software driver the tests use.
- The Vulkan memory totals are counters read with no lock. How much memory each memory type and each pool has in use - asked on every check of the memory load and, for the sampler count, on every trim - were maps behind a lock that each question took shared, and that counting a sampler in or out took exclusively. They are fixed arrays of atomic counters now (`VKResourceManager.cpp`): a question is a load, counting a sampler is one add, and three reader locks and two exclusive ones are gone. The record of what was allocated, which only allocating and freeing use, stays under its lock. Not run on a GPU beyond the software driver the tests use.
- The Vulkan render pass cache is read with no lock. `vk::get_renderpass` took a reader lock for every lookup that got past the one-entry cache in front of it; the passes are in the add-only lock-free map now (`Utilities/lf_u64_map.c`, key to handle), a lookup is a hash and a few loads, and two threads that miss the same key at once each make the pass and one is destroyed. The map gained `lf_u64_map_each`, for the destroy at shutdown. Not run on a GPU beyond the software driver the tests use.
- Finding the program for a draw takes no lock. Every draw that changes program looks up its vertex program, its fragment program and the pipeline of the two in the program cache, and each of the three lookups took a reader lock: two writes to a word the shader compiler threads share, and a wait whenever one of them was adding a program - on the render thread, in the middle of a frame. The three maps are `program_cache_map` now (`Program/ProgramStateCache.h`): buckets of chains, an entry pushed with a compare-and-swap and never moved, found with no lock; a pipeline's entry carries the pointer its readers load, null until whoever made the entry has linked it, which is what the placeholder under the lock was for. `test_shader_corpus` has six threads add the same 20000 keys in different orders: one entry a key, made by one thread, the same entry handed to all (fails without the look at what was pushed meanwhile). `reader_lock`, RPCS3's own name for the same kind of lock, is used 90 more times in the core; the render path's (texture cache, render pass and framebuffer caches, the shader interpreter) come next. Not run with a game or on a GPU.
- A game's file reads no longer go one at a time. `sys_fs_read` - the plain read, at the file's position, which is what most games load with - held its mount point's lock exclusively for the whole host read, so every read from the disc, or from the hard disk, by any thread and of any file, waited for the one before it. It holds no lock now: the read is counted on its file as a read at an offset is (`lv2_file::io_begin`), and the file's position is moved on with a compare-and-swap after the host read, done again from the new position if another thread moved it meanwhile (`libretro_vfs.cpp`) - so two threads reading one file on still each get a part of their own, and the position never passes the file's end. `test_vfs_positional` has four threads read one handle on at once, with a frontend that reads at offsets and with the two older kinds: every block is read by exactly one of them and the position ends at the end (fails on the position handled as it was). Writes, seeks and the rest still take the mount's lock. Not run with a game.
- A game's read at an offset (`cellFsReadWithOffset`, the third `std::shared_lock`) takes no lock. Every such read took its mount point's lock shared for as long as the host read took: all the files of the disc, or of the hard disk, on one word that each read wrote twice, and every read on a mount waited whenever anything on it was written, renamed or closed. A read is now counted on its own file (`lv2_file::io_begin`/`io_end`, two atomic adds on the file's line), and the one thing the lock was there for is kept another way: the host handle is taken away - by a close, or by a rename that has to close and reopen the file - only once no read is in flight, and no read begins while it is away. `test_vfs_positional` has three threads read while the handle is swapped under them 300 times (hangs or dies without the check for a handle that is away). Reads through the file's position (`sys_fs_read`) still take the mount's lock, exclusively: next. Not run with a game. Five `std::shared_lock`s are left.
- A game's file read or write into memory the emulator does not hand straight to the host (anything but the first 256 MB and the stack) went through a 64 KB `std::vector` that was allocated and zeroed for every call. The buffer is on the stack now: no allocation and no clearing on the way of a read. (The copy through it remains; reading straight into that memory is a separate question of which guest memory the host can be given.)
- Looking up an exported function takes no lock (`ppu_get_exported_func_addr`, the second `std::shared_lock`). It took the link tables' lock shared and went through two `std::map`s, the outer one keyed by the module's name. Every function's link entry is now also published, when it is made, in a map that only gains entries and is read with no lock (`Utilities/lf_u64_map.c`, C89), under a 64-bit key of the module's name and the function's id; the lookup is one hash and a few loads, and reads the address out of the entry as the word it is. The tables are still built under their lock. A key shared by two functions would hand one the other's address, so publishing checks it; `test_vfs_positional` holds all 3805 functions the emulator's own 153 modules register to it (none clash, and they use 3% of the map), and `test_lf_u64_map` covers the map itself, also under ThreadSanitizer. Not run with a game: a game's and the firmware's modules publish through the same four places. Six `std::shared_lock`s are left.
- An SPU function's module is hashed where it is written. To name the object a module compiles to, its bitcode went through `WriteBitcodeToFile`, which makes a 256 KB buffer of its own for every module, writes into that and copies the result into the caller's stream - here another buffer, made for each function too. The recompiler now writes with `BitcodeWriter` straight into one buffer of its own that keeps its room from one function to the next, and hashes it there; the string naming the CPU and LLVM is made once, not per function. Loading 200 functions from their objects takes 200 ms where it took 229 (`test_llvm_jit`). The objects' names change with this, so SPU objects kept by an earlier build are compiled once more.
- The first of the core's reader locks (`std::shared_lock`) is gone: the EEPROM bytes of `sys_ss`'s update manager. They were an `unordered_map` behind a reader-writer lock, taken shared for every read and exclusive, with a map node allocated, for every write. They are a fixed table of 64-bit words now (`Emu/Cell/lv2/eeprom_table.c`, C89): an offset and its byte in one word, found by hashing the offset, claimed and replaced with a compare-and-swap; a read is a few loads, a write allocates nothing, and nothing waits. `test_eeprom_table` (also under ThreadSanitizer) covers reads and writes, offsets that hash together, a full table, and four writers against six readers (fails when a writer does not recognise its own word). Seven `std::shared_lock`s are left.
- RPCS3's own engine for waiting on an atomic and waking it is gone: `atomic_t`'s `wait`, `notify_one` and `notify_all` go through libretro-common's new `retro_waitaddr` (over `retro_eventcount` and `retro_atomic`). `rpcs3/util/atomic.cpp` goes from 1414 lines to 181 - the hash table of 131072 entries (8 MB), the pool of condition handles, the per-platform sleeping (futex and futex_waitv, NtWaitForAlertByThreadId, keyed events, a mutex and condition variable elsewhere) are removed. A notify with nobody waiting - most of them: every thread state change, every lv2 object signalled - was a system call every time on Linux, 133 ns here; it is one read-modify-write now, 11 ns with the store. Windows searched its hash table there instead; that path is replaced by the same code and is not measured. A wait parks through one record of the waiting thread's, published under each address it names, on every platform, so waiting on several words no longer needs futex_waitv (Linux 5.16). First step of taking `atomic.hpp` out for `retro_atomic` used directly. `test_vfs_positional` wakes sleeping threads with `notify_all` and with `notify_one`, checks a bounded wait against its bound and the cost of a notify nobody hears (fails on the old engine's 133 ns); the whole of `make check`, which waits and wakes all through, passes on it. Not run with a game, and not on Windows.
- Two things every syscall and every call into an emulated library paid for a log are gone. Each syscall added one to a counter that all PPU threads share (the threads take the counter's cache line from one another on every call), for a thread that woke every second and wrote the counts into the log every ten: the counter and the thread are removed. And each syscall and library call wrote itself into its thread's call history - a division, to find the slot, and four stores - also when the history is not kept (the PPU call history setting, off), where it is one entry long and read by nothing: it is written only when it is kept. Two gates in the library tests.
- An error a game's call returns costs nothing when it is not logged. Games get errors back all the time - a lock that is taken, a wait that timed out, a file that is not there - and every one that is not marked as expected went through `error_code::error_report`: the function's name and the error were formatted into a string, the call's arguments after them, and the string was counted in a per-thread map of every such string the thread had ever made, to log each one only three times. All of that also with the log off, and the map only grew (152 bytes an error with a new argument in it). Now the report returns at once when its channel's level is not logged: 3.5 ns an error where it was 448 ns, and nothing kept (`test_vfs_positional`, 20000 errors with the log off; fails without the early return).
- A compiled shader goes to the Vulkan driver from where the compiler wrote it. `shader::compile` had the module copied out of the compiling thread's block into a vector of its own (an allocation and a copy for every shader, mid-game for a program a game brings up), handed that to `vkCreateShaderModule`, which keeps its own, and then kept the vector for the life of the shader with nothing ever reading it - beside the GLSL text, 20 to 50 KB a program, kept the same way. Now `spirv::compile_glsl_lent` lends the module in the thread's block until that thread compiles again, the driver is given those words, and the shader keeps neither them nor, once compiled, its text; the text is moved into the shader by the fragment and vertex programs, not copied; and a stage that comes as a built module is read where its owner has it. `test_shader_corpus` checks that every module the renderer compiled was lent from the thread's block and that the text is gone after the compile (fails when it is kept).
- The SPU recompiler's compiled code is kept between boots. Upstream compiles every SPU function again on every boot ("Building SPU cache"): it has an object cache for them, but only under the SPU debug option and marked testing only, because an object was named by its SPU code alone - with another setting, another CPU or another version of the recompiler the old object would have been loaded for a function that now compiles to something else. An object is now named by a hash of the LLVM module it is compiled from, as it stands before the passes, written out as bitcode, with the CPU and LLVM version: it is found only when it is that very module's, whatever the module was built from. When it is there, the passes, the verifier and code generation are not run - in `test_llvm_jit`, 200 functions of 40 to 400 instructions take 3.7 s to compile and 0.23 s to load from their objects on a later boot (code generation is 79% of a compile, the passes 14%). The objects go into one `llvm/objects.pack` beside the game's PPU cache and are lent to LLVM from it. Also gone from every compile: a disassembly listing of the function and a print of its whole module, both made for a debug file or a log that are not there (4% of a compile). `test_llvm_jit` checks that a second boot compiles nothing, in the opposite order too, and that a changed setting makes new objects where the old ones are not taken (fails when the name is made from the SPU code alone). Not run with a game.
- The on-disk shader cache is one file. It was a file for every pipeline and one for every fragment and vertex program - thousands for a game - each opened, read and closed when the game started, and when a new pipeline was made mid-game two files were looked for and up to three written. It is one `shaders.pack` now, the same pack the recompilers' objects are in: read once when the renderer starts, pipelines unpacked from that block, a fragment program's code lent from it where it lies (no buffer, no copy), and a new pipeline's three records written at the pack's end after a lookup in the index instead of on disk. A cache of files is moved into the pack the first time it is loaded and its pipeline files removed (the program files in `raw/` are left: other caches share them). For this the pack moved wholly into the C module (`Utilities/object_pack.c`: open, find, add, lend, read, each, over callbacks for the file), and the recompilers' cache uses that. `test_shader_corpus` stores pipelines, reads them back in the same session and a later one, checks that storing them again writes nothing and that the programs are lent, and moves a cache of files in (fails without the lookup before a write, and without the lend).
- `TTY.log` is gone. Every line a game printed to its TTY was written to that file as it came, on the game's own thread, on top of going to the log; and before that the text was copied out of the guest, searched for six words ("failed", "error", ...) to pick a log level, and now and then a dump of the thread's state was put together for a log message - all of it also when nothing was logged. What a game prints is in `rpcs3_detailed.log` (channel `TTY`) when the Detailed Log option is on; when it is off, `sys_tty_write` checks that the text is readable and does nothing else with it. A gate in the library tests keeps the file from coming back.
- A cache directory's compiled objects are one file, not a file each. Every part of a PPU module LLVM compiles was kept as its own object file, hundreds for a game with its firmware modules, and each boot opened and read every one of them twice: once only to see that it was there (`jit_compiler::check` loaded the whole object and threw it away), once to load it. They are now records in one `objects.pack` per directory (`Utilities/object_pack.c`, C89: the layout and a lock-free index). The pack is read once, whole, the first time its directory is asked for; an object in it is lent to LLVM from that block with no copy, and the block is freed when the last object lent from it is; `check` is a lookup in the index and reads nothing. A newly compiled object is written at the pack's end in place, straight from LLVM's buffer (`fs::file::write_at`, new: a write at an offset that leaves the handle's position alone, through the frontend's VFS v6 or `pwrite`), with no temporary file and rename. A record counts once its end mark is written, so a pack cut short by a crash counts up to there and is written on from there. Objects in files of their own, plain or `.gz`, are moved into the pack the first time they are loaded and their files removed. Nothing in it takes a lock. Measured here on Linux with the files already in the page cache, 600 objects of 150 KiB: 23 ms as files read twice, 20 ms as one pack, and 1200 opens become one; a cold disk and Windows, where an open costs far more, are not measured. `test_object_pack` (also under ThreadSanitizer) covers the layout, records cut short every way and the index from six threads; `test_llvm_jit` compiles into a pack, loads from it in the same session and a later one, moves loose and compressed objects in, and cuts a pack short and writes on (each shown to fail on a mutant).
- The emulator's logging is off unless asked for, and three costs of it are gone. Until now every message at RPCS3's default level was formatted on the thread that made it (two allocations a message), taken through one lock shared by all threads and kept in a list that only grew for as long as the core ran - standalone's `main()` tells the logger when it has started and the core never did - and then written to `rpcs3_detailed.log` and, deflated at the highest level on the log thread while the game ran, to a second copy, `rpcs3_detailed.log.gz`. Now the core says `logs::set_init`, so nothing is kept and nothing waits on that lock; the compressed copy is gone and what is waiting goes to the file in one write, not 32 KiB at a time; and a new core option, Detailed Log, off by default, decides whether there is a log at all. Off, `logs::set_ceiling(logs::level::fatal)` holds every channel at fatal errors - which is what puts "The emulation stopped: ..." on screen - so no other message is formatted or allocated for, and there is no log file, no writer thread and no 32 MB buffer for it. - The recompilers' cache is no longer compressed. There are now three textures, handed between the threads with one atomic exchange each and fenced on the GPU in both directions (`rpcs3/libretro/libretro_gl_frames.c`, C89, taking its GL functions from the caller). The renderer draws into one. retro_run copies the newest finished one once the GPU has drawn it. The renderer reuses a texture only once the GPU has finished the frontend's copy of it. Neither thread waits for the other. A texture is resized only when a frame of another size is drawn into it, and the frontend is told the size of the frame it was handed. A flip with nothing drawn hands over nothing, and the renderer's per-flip fence and frame counting are gone. `test_gl_frames` (in the library tests, on Mesa's software OpenGL through surfaceless EGL) runs a renderer and a frontend context on two threads and checks every frame shown is whole, newer than the last, and at the size it was drawn. With one texture, as before, it shows torn frames. Mesa's software rasteriser serialises GPU work by itself, so the fences are only exercised for real on a GPU.
- OpenGL: retro_run no longer waits on the CPU for the renderer's frame, and the renderer no longer checks and logs its framebuffer on every flip. Before blitting, retro_run used to wait up to 1 ms on the renderer's fence (`glClientWaitSync`), and past that blitted a frame the GPU had perhaps not finished. It now queues the wait on the GPU (`glWaitSync`), so the blit runs once the frame is drawn and retro_run never waits. On each of its several binds per flip, the renderer asked the driver for its framebuffer's status, which makes the driver validate it. It also logged a line for the first 120 binds and every 60th after. It now asks only when the framebuffer is a new one, and logs only when the framebuffer is not complete.
- The core's libretro code uses retro_atomic throughout. The pause watchdog, PKG installation, the VFS counters, the audio backend's flags, the OpenGL present fence and resource flags, and the presented Vulkan frame size used `std::atomic`. The frame size is now one word holding width and height, so a reader never gets the width of one picture and the height of another. The watchdog keeps its last-run time in milliseconds in a `size_t`, compared unsigned, so 32-bit builds work too. An unused `emu_mutex`, an unused `frame_ready` flag and an unused fence counter are gone. What is left of `atomic_t` there is RPCS3's own interfaces (its callbacks and the pad globals it declares). No behaviour changes; `make check` and the library tests pass as before.
- Software frames (a frontend without the hardware Vulkan context) go to retro_run without a lock or an allocation per frame. The renderer used to copy each readback into a new `std::vector`, 33 MB at 4K, and hand it over under a mutex retro_run also took, with the previous frame freed under that lock. It now copies straight from the mapped readback into a triple buffer (`rpcs3/libretro/libretro_sw_frames.c`, C89) and publishes it with one atomic exchange. retro_run takes the newest finished frame the same way, and it stays whole until the next take, since the frontend may show it again until then. A buffer grows only when a frame outgrows it, at a new resolution. The OpenGL build's and the no-OpenGL build's copies of the old handoff are both gone. `test_sw_frames` (in the library tests, also under ThreadSanitizer) checks that frames taken on one thread while another finishes 20000 are always whole, newer than the last, and unchanged until the next take. Publishing without the exchange makes it fail.
- The Makefile no longer regenerates its embedded sources on every build, so it no longer fetches the game patches from rpcs3.net each time. `embed` rewrites a source only when its contents change, so the source stayed older than `embed`, and make ran the step again on every build: the patches, the settings database, the vblank list and the UI icons. A stamp next to each source now records the run, and a deleted source is made again. `make check` fails if a build leaves any of them to be made again; the old Makefile does.
- Light guns reach the PS3 mice without retro_run taking the mouse lock or allocating. retro_run used to take RPCS3's mouse lock, which cellMouse, cellGem, the USIO board and the emulated guns hold on the game's threads, for every move, press and wheel turn, and each event grew a `std::deque`. Now it puts them on a lock-free ring per gun (libretro-common's `retro_spsc`, set aside when the handler is made). Whoever next reads the mice under the lock first replays them through RPCS3's own mouse code (`MouseHandlerBase::take_pending`), so the game gets the same events as before. If a ring fills while nothing reads the mice, the mouse catches up with where the gun points and what it holds once something does. `test_mouse_handoff` (in `make check`) checks the events the game reads, that retro_run finishes while the game holds the mouse lock, the catch-up after a full ring, and that the mouse only ever moves forward while one thread moves the gun and another reads. Leaving out the catch-up, or moving the mouse under the lock again, makes it fail.
- Input goes from the frontend to the game without the pad lock, and a race on a pad's status is fixed. Every retro_run took `pad::g_pad_mutex`, the lock the game's own threads hold in cellPad, to hand over the buttons and sticks, to count the connected pads and to read the rumble. A game thread holding it, or being switched out while holding it, made retro_run wait. Now:
  - Each pad's buttons and sticks are handed over in retro_atomics under a sequence count. retro_run writes them and never waits. cellPad, cellGem's emulated devices, the GameTablet and RPCS3's overlays copy them whole, and copy again if they caught a write in progress.
  - The rumble the game asks for is published as an atomic.
  - A pad's status (`m_port_status`) is a retro_atomic, changed with atomic or/and. retro_run used to set and clear its connected bit without the lock while the game changed the same field under it (registering or removing an LDD controller), so a change could be lost.
  - The buttons are no longer copied into a vector resized every run.
  `test_pad_handoff` (in `make check`) checks that what is handed over is what is read, including a copilot's buttons merged in. It also checks that the handover finishes while the game holds the pad lock, that 200000 reads during writes never see half of one handover, and that two threads changing the status lose nothing. Taking the lock again in the handover, or dropping the odd count while writing, makes it fail. The PS3 mice (light guns) still share RPCS3's mouse lock with cellMouse.
- The Vulkan images the frontend shows are shared between the renderer and retro_run without a lock. The libretro swapchain took a mutex on every acquire, release and image lookup. It also held that mutex while making new images on a resize, so a retro_run landing then waited for the whole resize. Now the images of one size form a set that the renderer's thread makes and publishes. Which images are held are retro_atomics in the set (`Emu/RSX/VK/vkutils/libretro_images.h`, C89). retro_run reads the published set and gives images back. A set replaced by a resize or restart goes on a lock-free stack, and retro_run frees it once the frontend is past it, as before; the old images stay alive exactly as long as they used to. Only a full teardown waits, on the renderer's thread, for a retro_run reading the set to finish. retro_run's list of images to give back is a fixed ring instead of a `std::deque`. `test_vk_images` (in the library tests, also under ThreadSanitizer) checks that no image is ever held twice between two threads and that every retired set is freed exactly once. Taking the retired sets with a load and a store instead of an exchange makes it fail.
- Frames go from the renderer to RetroArch without a lock or an allocation. The Vulkan handoff (`VKLibretro.cpp`) used to take a mutex several times every frame, on both the renderer's thread and retro_run, and its queue of finished images was a vector that allocated as images were queued and overtaken. With at most two frames ever waiting, the queue is now a single retro_atomic word holding the count and the two image indices, changed with a CAS. The frontend's running and stepping state are retro_atomics too. When the frontend has stopped, the renderer's thread waits for the next retro_run in 1 ms sleeps; retro_run never waits for the renderer, except in a step (Frame Advance, or the run after a pause), where it waits for the frame the game draws with the input it has just polled, as before. The OpenGL path lost a frame wait nothing called, along with the mutex and condition variable it took on every frame. `test_vk_handoff` (in `make check`) checks the order and overtaking, two threads with no frame taken out of order, no allocation, and stepping. The old code fails the allocation check.
- The game's audio goes to the frontend with no lock, no buffering of its own and no copies. retro_run used to wait up to 2 ms on a mutex shared with cellAudio's thread. It also pulled cellAudio's ring 2048 frames at a time into a 500 ms ring of its own, copied that out again and converted it to s16, using about 128 KB of stack. Now it pulls exactly what is due straight from cellAudio's ring into the buffer it hands the frontend. A frontend that takes floats (multi-channel output with `batch_float`, as RetroArch has) gets the game's floats untouched. Otherwise they are converted with libretro-common's `convert_float_to_s16` (newly synced, SIMD). cellAudio's thread opens, closes and sets the callbacks under a retro_atomic flag. retro_run never waits for it: if the flag is held it hands over nothing that run, and the time is owed to the next. `test_audio_frontend` (in `make check`) checks the floats arrive bit for bit, the s16 conversion, and that no run takes a millisecond while cellAudio's thread churns. The old code fails the float check.
- CI checks that the per-game data the core carries reaches the games. It checks that every executable and patch a plain scan of the file finds is read, with no error. It also checks that a sample of the games the patches name get their patches as core options (every 25th, since each lookup reads the whole file again). `test_vblank_list` (in the library tests) finds every title ID of vblank_unlock.txt in its block, again with Windows line ends. Its reader is now `rpcs3/libretro/vblank_list.c` (C89). Both lists were found to work; unlike the settings database, nothing was missing.
- The core calls itself ParaLLEl PS3 to the frontend, as its info file already did; it said RPCS3, so RetroArch's menu and title showed "RPCS3". RetroArch keeps a core's overrides, remaps and per-core save folders under that name, so those made under "RPCS3" are now looked for under "ParaLLEl PS3". The core's own files (system/rpcs3) stay where they are. `load_test` (in `make check`) checks the name.
- Recording for games (cellRec) hands frames and audio between threads without locks or per-frame allocation. The RSX renderer, cellAudio, cellRec's own thread and the encoder used to share queues behind mutexes, with a new buffer for every frame. They now pass slots through libretro-common's lock-free `retro_spsc` rings (newly synced). A frame's buffer is swapped in and out of its slot, so after the first few frames no buffer is allocated. Audio goes in blocks of 256 samples into storage set aside when recording starts. A full queue drops the frame, as the old queues did when the encoder fell behind; only cellRec's flush at its close waits for room. Stopping a recording clears the queues without stopping either side. `video_provider`, which hands the renderer's frames and cellAudio's samples to whichever recorder is active, publishes the recorder through an atomic pointer. Replacing it waits on the PPU thread, never on the renderer or cellAudio. `retro_atomic.h` is synced for its C++ casts (RetroArch), which RPCS3's `-Werror=old-style-cast` needs. `test_video_sink` (in the library tests) runs a producer and a consumer through 20000 frames and blocks, also under ThreadSanitizer. It also checks that buffers are recycled, the drop and wait behaviour, the clear and the audio blocks.
- Per-game settings from RPCS3's database are applied again, so Demon's Souls draws its world instead of only its HUD on black. It needs Write Color Buffers, which its entry turns on. The lookup kept pointers to member names that rjson had already reused. Of the 2242 games in the database the core carries, only the first two were ever found; every other game ran on the user's settings alone. The lookup is now `rpcs3/libretro/config_database.c` (C89), which keeps only whether each name is the one it wants. `test_config_database` (in `check` and the library tests) looks up every entry against a second reader; the old lookup misses 2240 of them.

It builds TableGen for the machine running the build, generates what LLVM's build generates, compiles the libraries the core's components need - the JIT, the passes, the X86 or AArch64 target, the perf listener on Linux - into one archive and links it in; the submodule is fetched once when it is not there. The source lists, flags and TableGen runs, and the headers LLVM's configuration writes for Linux, Windows and macOS, come from LLVM's own build description through rpcs3/libretro/make/llvm/gen.py and are committed, so no CMake is involved. `SYSTEM_LLVM=1` takes the system's LLVM through llvm-config as before; `HAVE_LLVM=0` builds without it. Intel's VTune JIT listener is left out (its sources are not in the submodule). - Recording for games (cellRec: a game recording its own play, or a clip of it, to an MP4) goes through libretro-common instead of FFmpeg, and FFmpeg is gone from the core: its submodule, its CMake target and finder, the Makefile's download and `SYSTEM_FFMPEG`, and the CI steps that built it for Android and Windows. Video is encoded by libretro-common's MPEG-4 Part 2, H.264 and motion JPEG encoders, audio by its AAC-LC encoder or as u-law or big-endian float PCM, all at the bit rates cellRec asks for, and written by its MP4 muxer straight to the file through filestream. The game's frames, or the renderer's, are scaled to the recording's size by libretro-common's scaler (after a box average when they are at least twice its size) and converted to YUV 4:2:0 by its new RGB conversion. Everything is allocated when a recording starts, except the scaler's tables, made again when the input size changes. Different from before: no B-frames (H.264 is Constrained Baseline, for Main Profile too); motion JPEG steers its quality toward the bit rate frame by frame; u-law recordings are written (FFmpeg's u-law encoder takes only 16-bit samples; the old code asked it for floats and stopped with an error); the first frame shows from the start of the file; a recording holds up to four hours. cellSearch now lists a motion JPEG MP4 as an unknown codec, as it did with FFmpeg, not as MPEG-4. CI records each video codec with each audio format from each kind of input (larger RGBA and BGRA frames, ARGB and YUV frames at the recording's size), has FFmpeg read the files back, and checks the codecs it names, each frame's time (a skipped frame leaves a gap), every frame against the picture (42 to 50 dB PSNR), and the audio against what went in, at no delay (35 to 47 dB SNR; float PCM exact). Not tried with a game yet.
- Music and videos (cellMusicDecode, cellSearch): WMA tracks play from their first sample to their last, at the length the file states. libretro-common's WMA decoder now drops the encoder's priming frame and plays the last frame's tail; standalone RPCS3, through FFmpeg, drops a frame of the audio at the start (46 ms at 44.1 kHz). - Music for games (cellMusicDecode: a game playing the user's music, and cellSearch and the media list overlay listing it) goes through libretro-common instead of FFmpeg: a track is found by its bytes, not its extension, and decoded by audio_transfer - MP3, AAC (MP4/M4A and ADTS), WMA, ATRAC3 and ATRAC3plus (.oma, .at3), WAVE, FLAC, Vorbis, Opus, AC-3 - folded to stereo and resampled to 48 kHz with libretro-common's sinc resampler; its title, artist, album, genre, track, disc and date are read by rtags; videos are listed by libretro-common's MP4, Matroska, MPEG program stream, AVI and ASF readers. The file is mapped where it lies, not opened through FFmpeg's I/O. CI plays files FFmpeg wrote - MP3 at 44.1 kHz, AAC, WMA2, FLAC 5.1, mono WAVE at 22.05 kHz, Vorbis at 32 kHz - and the sound is FFmpeg's, resampled as standalone RPCS3 resamples it: within 51 to 83 dB of it, mono at -3 dB on both sides and 5.1 folded as before; the tags are ffprobe's, and the codecs and lengths of the files and of six videos (MPEG-4 and AVC in MP4, AVC in Matroska, MPEG-1 and MPEG-2 program streams with MPEG audio or AC-3) are what cellSearch had from FFmpeg. Different from before: an MP3's length no longer counts its encoder padding (FFmpeg's estimate did); Vorbis, Opus and FLAC in Ogg have their tags listed (FFmpeg gave cellSearch none); the year of a date such as "2004-05-01" is listed, where only a bare year was. Not tried with a game yet.
- Video decoding for games (cellVdec: the movies and cutscenes in AVC, MPEG-2 and MPEG-4/DivX) goes through libretro-common's rh264, rmpeg1_video and rmpeg4_video instead of FFmpeg's decoders, and the pictures are converted for the game by libretro-common's YUV conversion instead of swscale. CI decodes streams FFmpeg encoded, with B pictures, and every picture is FFmpeg's - the same bytes in AVC, within one level in MPEG-2 and MPEG-4 - in display order, with the time stamps and user data of the access unit it came from and its picture type; B-skip and PB-skip drop the pictures they did; RGBA and ARGB come out within 3 levels of swscale's, UYVY the same. RGB is converted in the colour matrix the game asks for (BT.601 or BT.709), where swscale always used BT.601. MPEG-4's frame rate comes from the time between pictures, where FFmpeg's often fell back to 30. The decoded pictures go into buffers kept in a lock-free pool and reused, where a frame was allocated for every picture, and the alpha plane for RGBA output is gone. AVC decodes on one thread, about 80 pictures a second at 1080p on CI's machine. Not tried with a game yet.

- Video post-processing for games (cellVpost: a decoded picture to RGBA for the screen) goes through libretro-common's YUV conversion and scaler instead of FFmpeg's swscale. - The RSX blit engine's scaled and converting copies done in software (NV3089 with a scale, or between R5G6B5 and A8R8G8B8: some games' 2D blits, video and HUD layers) go through libretro-common's scaler instead of FFmpeg's swscale, the first of the core's uses of FFmpeg to move. Both are built into the core, not DLLs of their own, but asmjit's API was declared dllexport (its CMake variable ASMJIT_STATIC never reached the compiler) and RtMidi was built with RTMIDI_EXPORT; ASMJIT_STATIC is now defined for asmjit and the code that uses it, and RTMIDI_EXPORT is dropped, as the Makefile build has them. Seen on the Makefile's Windows build, where this took some 230 exports off the DLL; not tried on the CMake Windows build yet.
- Makefile, Windows (`platform=win`, MinGW-w64): the core it builds now loads. It needed MinGW's libstdc++-6.dll beside it (the link switched back to shared libraries before the C++ runtime came in), and exported some 230 of asmjit's and RtMidi's functions along with its own; it is now linked statically and exports its libretro functions and the NVIDIA/AMD GPU-selection flags only, and it links GLEW as the CMake build does on MinGW. RtMidi has its MIDI backend on Windows (WinMM) and macOS (CoreMIDI), as RtMidi's own build has by default, for Rock Band 3's MIDI instruments. Checked by building it with MinGW-w64 GCC 13 on Linux and loading it under Wine: it needs Windows' own DLLs, vulkan-1 and opengl32, nothing else. `libretro_vfs.cpp` includes `<sys/stat.h>` on Windows, which GCC's MinGW headers do not bring in by themselves.
- The core builds without CMake too: `make` at the top of the tree, as libretro's other cores build (Makefile, with the source lists in Makefile.common). It builds what the CMake build builds, from the same sources with the same flags: LLVM (21 or newer, found through llvm-config, linked statically), RPCS3's prebuilt ffmpeg (downloaded as the CMake build does, or `SYSTEM_FFMPEG=1`), GLEW statically; the config database, the overlays' icons, the VBlank list and RPCS3's game patches (fetched from rpcs3.net, `EMBED_PATCHES=0` to leave them out) are compiled in by a small C tool (rpcs3/libretro/make/embed.c) whose output is the CMake build's, byte for byte. The core exports its libretro functions and nothing else. `make check` loads it with every symbol resolved; CI builds it this way on Linux with LLVM 22. The macOS (`platform=osx`) and Windows (`platform=win`, MinGW-w64) sections follow the CMake build but have not been built yet.
- The Linux core no longer leaves a function of ffmpeg's undefined: the CMake build linked the prebuilt ffmpeg libraries with libavutil before libswscale, so `ff_init_half2float_tables`, which swscale calls and avutil has, was never taken in. The core loaded anyway, as RetroArch resolves functions when they are first called, and would have stopped at the first scaling that reached it; a loader that resolves everything at once (`RTLD_NOW`) refused it. avutil is now linked last.
- RPCN's messages (rooms, matchmaking, messages, scores, TUS) are read and written by the core's own code instead of the protobuf library, which is no longer built, nor is the Abseil library it fetched from GitHub at configure time (the protobuf submodule, `USE_SYSTEM_PROTOBUF` and the `protobuf_*` options of the CI scripts are gone). The code is made from RPCS3's `np2_structs.proto` by a script beside it (`rpcs3/Emu/NP/generated/np2_structs_gen.py`), with the names protobuf gave it, so RPCS3's code that fills and reads the messages is as it was. What goes to the server is the same, byte for byte, and what comes from it is read the same: CI reads 16,000 messages the protobuf library wrote, read in other ways it accepts, or broken, and every one must come out as protobuf made of it (RPCS3's own protobuf, at the commit it pinned, agreed with them all). A reply is read where it lies in the packet - its strings and bytes are not copied out - and a request is written straight into the packet that is sent, where it was written into a string, copied into a buffer and copied again. Not tried against the RPCN server yet.
- Text is drawn by libretro-common's rtt instead of stb_truetype, and stb is no longer in the tree (its submodule is gone): the overlays' text (the home menu, messages, trophies) and the fonts games draw with cellFont. Glyphs are placed exactly as before - CI packs whole pages of a TrueType and a CFF (CJK) font both ways and every glyph's place, size and advance is the same - and they come out closer to the true shape of the font: rtt follows curves more finely than stb did, about four times closer on average and three times in the worst texel, and still draws a page in about half the time. A font a game opens is kept in a table of the core's instead of in the game's memory after its CellFont, which stb's state overwrote; its glyphs are drawn straight into the game's surface instead of into a buffer allocated for each one and copied. Not tried with a game yet.
- Save states no longer go through a file: Save State has RPCS3 write the machine's state into memory the core keeps, and Load State boots from RetroArch's buffer through that same memory, instead of writing `<title>_libretro.SAVESTAT.zst` to disk and reading it back. A save copies the state once, into RetroArch's buffer; a load copies it once, out of it. The memory is kept for the session and reused by the next save, so it is not taken again each time. Not tried with a game yet.
- RPCN: dropping the connection (a failed login, a reconnect) no longer frees it under the reader and writer threads: it waits for both to have left it, which they do within 50 ms. Before, the connection could be freed while the reader was still in it. The two threads are told apart from it with atomics instead of a mutex each, and the packets to send go through a lock-free queue instead of a mutex-guarded list. The writer thread no longer ends for good after a failed send, which left later connections with nothing to send their packets. Not tried against the RPCN server yet.
- PNG decoding for games (cellPngDec) takes its decoder from a pool of eight that closed streams give back, instead of making one, with its 64 KB file buffer and its row memory, at every open and freeing it at every close. Games open PNGs as they load; once the decoders have decoded an image of a size, opening another takes no memory. The pool is lock-free and is emptied when the emulation ends. CI's PNG comparison now decodes all its 9440 cases with one decoder, reset in between, as the pool uses them.
- YAML goes through libretro-common's ryaml (reading) and ryaml_writer (writing) instead of yaml-cpp, which is no longer built (its submodule is gone): the configuration and per-game configurations, the patches and the patch configuration, games.yml, the disc image cache, the players' history, music playlists and the PRX validation files. A document is read where it lies - from the file's buffer, or from the string a setting comes in - instead of being copied into a tree of its own. The settings database (`config_database.dat`), which is JSON, is read with libretro-common's rjson in one pass that stops at the game's entry. Files written before read as they did: CI reads an excerpt of RPCS3's patch.yml (anchors and the `load` entries that name them, values on the line below their keys, escapes) and 300 documents written by yaml-cpp's emitter, and checks every tree against yaml-cpp's, then writes each again as the core now does and reads it back. What the core writes is laid out as before, two spaces a level; a double is written with the fewest digits that read back the same. Not tried with a game yet.
- RPCN's connection to its server is encrypted by libretro-common's own TLS client instead of wolfSSL, which is no longer built (its submodule and the `USE_SYSTEM_WOLFSSL` option are gone). RPCN reads on one thread and writes on another at the same time, which wolfSSL did through its "write dup"; libretro-common's client now has a duplex mode for this with no lock, where a key update the server asks for is answered by the writing side. The server's certificate is still not checked. The handshake waits on the socket for what it needs instead of spinning, for 10 seconds at most, and may now be TLS 1.3 where the server offers it. The error RPCN shows when this fails reads "TLS Error" instead of "WolfSSL Error". CI runs a reader and a writer thread on one connection against a local OpenSSL server, the way the RPCN client does, under AddressSanitizer and ThreadSanitizer. Not tried against the RPCN server yet.
- BC1, BC2 and BC3 (DXT) textures, for a GPU that cannot sample them itself (some phones), are decoded on the CPU by libretro-common's rdds block decoders instead of RPCS3's copy of bcdec, which is gone. The texels are the same (BGRA, straight into the upload buffer as before), except the interpolated alpha of BC3: bcdec cut each step of the ramp down, rdds rounds it to the nearest value, which raises it by one on about a quarter of those texels. A GPU that decodes BCn itself (most desktop ones) is not affected. CI checks the decoders against bcdec at the commit RPCS3's copy came from, over random blocks and every BC3 alpha ramp. Not tried with a game yet.
- SoundTouch is gone, and with it RPCS3's Time Stretching (Enable Time Stretching and its threshold, in the config and the home menu's audio settings). The core already kept it off: it only worked on top of cellAudio's own buffer, which the core also keeps off, and RetroArch's dynamic rate control keeps the sound in step with what it plays. The game's sound goes straight into the buffer RetroArch reads from, as it did. A config or database entry that still sets the two options is ignored.
- Save states. RetroArch's Save State and Load State now work, through RPCS3's own savestates: a save stops the emulation, writes the whole machine to a zstd-compressed state and boots back into it, which takes a few seconds and a few hundred MB; a load boots the state. The state is read from RPCS3's file straight into RetroArch's buffer. Its size is that of the state itself, which varies, not a fixed maximum. They are for saving and loading only: making one every frame is out of reach, so rewind, run-ahead and netplay stay off (the .info file says "basic"). Saving fails, as in RPCS3, while SPU threads cannot be paused where a state can be taken (SPU Savestates-Compatible Mode helps), while a video decoder is open or while the game is saving; RPCS3 says which on screen and the game carries on. Not tried with a game yet.
- HTTP goes through libretro-common's net_http instead of libcurl, which is no longer built (its submodule and the `USE_SYSTEM_CURL` option are gone): the clans server's requests, over https with libretro-common's own TLS client (no certificate checked, as before), and UPnP's. net_http keeps its connections and DNS cache for one thread, so every transfer runs on one network thread that callers hand their request to over a lock-free queue and wait on their own completion for; there is no lock. A clans request now gives up after 30 seconds instead of waiting for ever. The clan ticket and member data are base64-encoded with libretro-common's encoder instead of wolfSSL's (which stays, for RPCN). CI posts a clans request through net_http, built as the core builds it, to a server on the runner and checks the request and the answer, including an HTTP error page, which is still taken as the answer. Not tried against a clans server yet.
- JPEG and GIF decoding for games (cellJpgDec, cellGifDec) and the overlays' images (icons, backgrounds) go through libretro-common's rjpeg, rgif and rpng instead of stb_image, which is now built only for stb_truetype (the overlays' fonts). The game's buffer is decoded where it lies instead of being copied first, and the pixels go straight into the game's output buffer in the format it asked for, with no image-sized staging copy; a GIF is decoded in a single pass, and the decoder's memory and the read buffer for a file are taken once on each thread that decodes and kept. CI compares the three decoders with stb_image 2.30, the version RPCS3 pins, over PNGs, JPEGs and GIFs of every kind: the same pixels, except where stb_image was wrong - it swapped red and blue in a GIF's background colour, and in a 4:2:2 JPEG it weighed the last chroma column the wrong way round. RGB output from cellJpgDec was three-byte pixels cut from four-byte ones (scrambled); it is now RGB. A broken file is still refused with the same error, but may leave part of the output buffer written. Not tried with a game yet.
- PNG decoding for games (cellPngDec) goes through libretro-common's rpng_rows instead of libpng, which is no longer built. The pixel conversions games ask for (palette to RGB, transparency to alpha, adding, removing or moving alpha, 16 to 8 bits, RGB to gray) are done as the libpng the module used does them; CI compares the two byte for byte over every PNG colour type, bit depth and output format, interlaced or not, for both whole-image and row-by-row (progressive) decoding. A broken PNG now returns an error to the game instead of stopping the emulator. RGB-to-gray output of a PNG with colour chunks (gAMA, sRGB, cHRM, mDCV) comes out as libpng 1.6.59's did too, the version RPCS3 built: the channels weighted by the file's chromaticities, mixed in linear light when the file has a gamma, through the same tables, built once when the header is read. A row that needs no conversion is now handed on where the decoder left it instead of being copied first. Not tried with a game yet.
- UPnP port forwarding (Network > UPnP) goes through libretro-common's net_upnp instead of miniupnpc, which is no longer built. The router found before, saved in `upnp.yml`, is used again without a new search, and a port the router has taken is tried as the next one up, as before. Not tried with a real router by anyone yet.
- XML goes through libretro-common's rxml instead of pugixml: trophy configurations, the redump database check and the clans server's requests and responses. The trophy and redump files are read straight into the buffer the parser keeps, without the copy they went through before. Not tried against a clans server by anyone yet.
- RPCS3's own compression goes through libretro-common's Deflate instead of zlib: the compressed log (`rpcs3_detailed.log.gz`, still complete up to its last line after a crash), gzip savestates, IRD files, PKG/SDAT and SELF decompression and the IRD checksums. Files written before read as they did, and what the core writes is standard gzip (checked in CI). zlib is no longer built at all (the in-tree LLVM and curl builds are told not to use it).
- Savestates are compressed and read with libretro-common's Zstandard instead of the zstd library, which is no longer built. Savestates made before load as they did, and the ones the core writes are standard Zstandard frames, which the reference zstd reads (checked in CI). They come out a little larger: on one 16 MB sample 9% larger than zstd's, written at the same speed.
- Namco System 357/369 arcade games: new option Core > Arcade USIO Mode, Fighting Games (default, as standalone) or Shooter Games, which the arcade board reads its buttons by. RetroArch's light guns, or the mouse RetroArch makes one of, are the PS3's mice now, one per port, which the shooters (Deadstorm Pirates, Dark Escape) aim with; the core used to have no mouse at all. In Shooter Games ports 1-2 and 3-4 trade places, as those games take the board's players 3 and 4 as their players 1 and 2, and the gun's trigger, second trigger and start reach the board as it expects. The controls list names what Select, L1, L2 and R2 are on the arcade board: Test, Card, Coin and Service. Not tried with an arcade game yet.
- Linux: content loaded again in the same RetroArch, after closing it, starts from scratch: the core was never really unloaded, so the second start ran on the first one's state and, with OpenGL, drew a flipped and broken picture. RPCS3's logging kept two buffers per thread whose destructors tied the core to the thread that used them until it ended, and RetroArch's main thread logs too and never ends; they are plain buffers now.
- Linux, Android and macOS: a crash is no longer the core's to end. RPCS3's fault handlers (segfault, illegal instruction, broken pipe) are taken out when the core is unloaded and the ones there were before put back, as on Windows already; left in, a later crash anywhere in RetroArch jumped into code that was gone. A fault the core does not handle goes to the previous handler instead of ending RetroArch from inside the core, so the system's crash report (Android's tombstone) is written and names the fault (sco8487).
- The firmware is found whatever the case of its name: a `PS3UPDAT.pup` was not installed on Linux and Android, where only `PS3UPDAT.PUP` was looked for (demifiend9).
- A GPU that lacks a Vulkan feature RPCS3 requires (shaderUniformBufferUnsizedArray, on Mali phones) no longer hangs RetroArch: the core tries RPCS3's Vulkan device before the boot, and refuses the content with a message when it cannot be made. A game whose boot still fails part way has the threads the boot started stopped and its disc image let go. RetroArch used to stay on "Unloading core..." until it was killed (sco8487).
- Linux and macOS: the core raises the limit of open files as standalone RPCS3 does (4096 on Linux). With the frontend's, often 1024, the NVIDIA Vulkan driver ran out of file descriptors as the first game started, and the game froze at once with "Out of host memory (VK_ERROR_OUT_OF_HOST_MEMORY)" (demifiend9, RTX 4050). The log says the limit the core got.
- Reset works for a game loaded from a disc image (`.iso`): it used to close the content with "The game could not be restarted", because stopping the emulator unmounts the image and the reset booted the game from it without mounting it again.
- Android x86_64 (buildbot): ffmpeg is built with its x86 assembly, as the buildbot's Android image now has nasm; it decodes the games' videos faster there.
- The `libretro-latest` release is gone: libretro's buildbot builds the core for every platform it had, and installs it through RetroArch's Online Updater, while the release had fallen behind. Test builds stay as artifacts of the CI workflow.
- Android: a game behind a `saf://` path, as the Play Store RetroArch gives for folders it was granted, is read through RetroArch's VFS for directories too: listing, stat, creating, removing, renaming and copying, not only opening files. That is what an unpacked game in such a folder needs. Ordinary paths are untouched. Not tried on a real SAF path by anyone yet.
- New option Disk Cache Size (1 GB by default, 5 GB, Wipe on Exit or Unlimited as before) for the games' cache on `dev_hdd1`: with a size RPCS3's own disk cache limit is used, deleting the caches used longest ago when a game is loaded and when it is closed; Wipe on Exit deletes all of it at both points (NNshi).
- The settings database in `GuiConfigs/config_database.dat` is replaced by the core's only when it is missing or carries an older `timestamp` than the core's; it was replaced whenever its bytes differed, so entries edited by hand did not stay (NNshi).
- New option GPU > Aspect Ratio, 16:9 (default) or 4:3, as RPCS3's own setting: with 4:3 a game with a native 4:3 mode renders for it, and the core tells RetroArch the picture is 4:3 (unless Stretch to Display Area names another ratio); the picture fills the frame, so Stretch to Display Area does not have to be set for it. Takes effect when the game is started (NNshi).
- Frame Pacing is an option again (Emulator clock by default, or RetroArch: one PS3 refresh per frame RetroArch shows). It had been removed on one tester's result, which he could not repeat (NNshi).
- Pause and Frame Advance with the Vulkan renderer: once RetroArch stops asking for frames, the game waits after the frame it is drawing, and each Frame Advance step lets it draw exactly one frame and shows that one, drawn with the input of that step. The game used to run on for a tenth of a second and a step let 4-6 frames through (NNshi).
- Sound after unpausing: the first frames after a pause handed RetroArch up to four frames' worth of sound at once, which with RetroArch's audio sync on made the frame rate drop and swing for seconds. A pause is no longer made up for (NNshi).
- Linux: the core no longer links libGL, libGLX and libX11, so it loads on a system without X11. It links libOpenGL for OpenGL itself, and the GLX and Xlib functions it shares RetroArch's context with on an X11 session are found at run time, in RetroArch's own libraries.
- VBlank Frequency has a new choice, From List: a game named in `vblank_unlock.txt` runs with a 120 Hz VBlank - shown at 60 frames a second when it is a 30 fps game, at 120 when it is a 60 fps one - and any other game stays at 60 Hz. The list ships with the core and is written to `system/rpcs3/` when it is not there; the core never overwrites it, so titles can be added. It comes from the RPCS3 wiki's list of VBlank-compatible games and NNshi's testing.
- Frame Pacing is removed, option and code: the game's frames are timed by RPCS3's own clock, as in standalone. The other choice, one VBlank per frame RetroArch shows, added input lag and was better in no case tested.
- Save Data Slot is removed: the game's save list is always shown in the picture. The core picks the first entry itself only when the list cannot be shown.
- Default Resolution's tooltip warns against using it to upscale; Resolution Scale is for that.

## October 2026

### Upstream

- Merged up to upstream RPCS3 build 20243 (v0.0.43), after builds 20147 and 20149. The core reports upstream's version and build number, with this repository's commit after it, and logs both at start.

### Picture

- Vulkan through RetroArch's own hardware context: the renderer draws on RetroArch's device and hands each frame over as an image, with no copy through system memory. Finished frames are handed over in order, each once, so the picture no longer judders against RetroArch's refresh. The context is kept across RetroArch's video driver rebuilds, and replaced images stay alive until RetroArch has moved on.
- Before the first picture the Vulkan frame is 720p at the Resolution Scale, so the compilation progress is drawn sharp.
- A game no longer holds RetroArch through its PPU compilation at boot.
- Output Scaling and Vulkan Frame Readback are no longer options. Frame Pacing defaults to the emulator's clock.
- macOS: Vulkan through MoltenVK, no OpenGL in the core.

### Sound and pads

- Surround sound: the Audio Format option (Stereo by default, Surround 5.1, Surround 7.1) is what the PS3 reports to games, and with 5.1 or 7.1 the channels go to RetroArch's multi-channel output.
- Rumble through RetroArch's rumble interface.
- Pads report a PlayStation 3 controller, as standalone's handlers do, and the sticks reach full diagonals.

### Games and files

- PKG files are installed without being started, into the configured dev_hdd0, and the `.rap` licenses next to a PKG are installed with it.
- RPCS3's game patches (`patch.yml`) and its settings database ship with the core; Database Settings Override says whether the database's per-game settings apply. They, and the in-game overlays' icons, are rewritten when their contents differ.
- Save data is picked from the game's own list, shown in the picture.
- Emulate BD-ROM Read Speed as a core option.

### Core options

- The options carry RPCS3's own names and sections, in the layout NNshi proposed: CPU, GPU, Scheduling, Network, Debug, Core. Each option does what it says; several that were never read are now connected.
- Options for Disable Blit Engine Upscaling, RPCS3's performance overlay and the Resolution Scale Threshold.
- VBlank NTSC Fixup on by default, as in RPCS3.
- PSN Status says where an RPCN account comes from.
- On big.LITTLE ARM CPUs the compiler threads default to the big cores, and only the efficiency cores are left out.

### Builds

- macOS cores for Apple Silicon and Intel, and Android x86_64 next to arm64-v8a.
- The Windows core is `rpcs3_libretro.dll`; Linux links curl in instead of depending on Debian's libcurl-gnutls.
- Recipes for libretro's buildbot: Linux, Windows (cross-built with llvm-mingw), Android and macOS.
